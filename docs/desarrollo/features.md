# Features and how they behave

What the app does and the rules behind it, from the point of view of whoever runs it or uses it. The settings that go in `.env` are in [configuration.md](configuration.md); the code behind each rule is in [architecture.md](architecture.md).

## Seasons

A season is a calendar year. It is **never written by the app**: the `season` column of `users_games`, `game_timers` and `users_achievements` is generated by the database from the row's own date (`started_date`, `start_time`, `date`), so it can never disagree with it. To put a library entry or a session in another season, change its date. The running season is the year of today's date on the server (`api/src/utils/seasons.py`); keep `TZ` set so the season changes at local midnight.

The library of the 2023 and 2024 seasons (kept in the `_archived_users_games_*` tables since the yearly tables were retired) is restored into `users_games` by migration 011, so every past session has its library entry. The archive tables are left as they were.

## Notifications and scheduled jobs

Notifications are managed from the admin panel (**Notificaciones → Envíos** and **Canales**), except the Telegram bot's token and chats, which are in the server's `.env` (the panel shows whether they are set in **Sistema → Servicios**):

- **Settings** live in the `app_settings` table: general notifications switch, admin-alerts switch (independent), weekly summary on/off + weekday + time, monthly recap on/off + day + time, and the AI settings. **The keys of outside services are not among them**: `TELEGRAM_TOKEN`, `TELEGRAM_GROUP_ID`, `TELEGRAM_ADMIN_CHAT_ID` and `AI_API_KEY` are read from the environment every time and never stored (`env_only` in `utils/settings.py`; migration 035 deleted the rows that used to hold them, like `RAWG_API_KEY` and the SMTP password, which never were), so a copy of the database (a backup, a dump loaded on a laptop) cannot run the group's bot or spend the AI quota. The panel only says whether each one is set (`GET /manage/settings` returns `{is_set}`, never the value) and `PUT /manage/settings` refuses to change them. **Without them the API starts anyway**: the panel says what is missing (the home card and the Telegram card: "Telegram no está configurado"), nothing is sent by Telegram and the AI is not used. Only the **bot** refuses to start without `TELEGRAM_TOKEN` and `TELEGRAM_GROUP_ID`. The API and the bot both read them from their own `.env`.
- The **bot** reads its token and chats from its own environment. Changing them means editing `.env` and restarting the API and the bot (the API keeps no copy: `docker compose up -d` recreates both).
- **Scheduled jobs** run inside the API process (`api/src/utils/scheduler.py`), so no external cron is needed: weekly summary (private message to each active user with a Telegram id or a push device), monthly recap (see [Recap](#recap-wrapped); off until an admin switches it on), (the pinned timer notification is only sent when the timer starts: its periodic refresh is switched off, `TIMER_NOTICE_REFRESH` in the scheduler), hourly forgotten-timer check that reminds once per timer (after 4 hours by default; each user can switch it off, choose whether it reaches them by Telegram and/or push, and choose their own whole number of hours, 1-24, in Profile → Ajustes → Notificaciones; a channel the user cannot be reached by, such as Telegram without a linked account or push without a device, does not count, and with none left no check is made), daily 05:00 check (announces the streaks lost the day before), daily 09:00 wishlist check (see [Wishlist](#wishlist-and-upcoming-releases)). Each run is recorded in `job_runs`, so a restart never repeats a run, and a job that was due while the API was down still runs when it returns (weekly summary: within 6 hours). Achievements and ranking announcements are event-driven: when a timer stops, a session or library entry changes (an admin's changes check the player silently) or an admin asks for it, everything is checked; when a timer starts, only what a running timer can unlock (early riser, nocturnal, new year, the release day of a game, the ones about the world outside the app, teamwork, all together) and the "new game" notice, once per game and season; completing a game also checks the completed-games achievements. A manual session, or a change to a session of your own, announces the achievements it earns (the same notices a timer gives; the rankings and the other players' sessions are not announced) and revokes, without a notice, what it no longer holds; an admin's changes stay silent. Totals, rankings and streaks are never stored: they are computed from the sessions when requested, so a new season simply starts at zero.
- **Inactive users never appear in the bot**: its rankings ask for `GET /statistics/rankings?...&only_active=true`, and the ranking-change announcements (hours and games) are computed without them. The app itself (rankings page, statistics) keeps counting them.
- A player cannot type their Telegram id: nothing proves it is theirs, and someone else's id would send them the player's private notices. It is linked by the bot's `/activate` in the group, or by an admin for anyone (the profile route refuses a player any id other than their own with a 403); it is unique. The profile shows it read-only, with a button to unlink it (`PATCH` with `telegram_id: null`, which a player may do) and one that sends a private test message to the saved id (`POST /users/{username}/telegram-test`, only for oneself, ignores the notification switches, at most 3 tries in 5 minutes) so the player can check it is right.

## Push notifications (installed PWA)

A second channel next to Telegram, **on by default**, with nothing to set up: the API creates its VAPID keys (one pair for the whole server, shared by all users) on the first start and uses `SMTP_EMAIL` as the contact towards the push services unless **Sistema → Servicios** sets another one (there too, the keys can be regenerated) or **Notificaciones → Canales → Avisos en la app (push)** turns the feature off. The keys are stamped with the deployment that made them (`ENVIRONMENT` + `PUBLIC_URL`, setting `push.vapid_origin`) and push stays off, with an error in the log, while that stamp is not this deployment's: a production dump restored in dev keeps the real devices and keys, and must not notify them. There the fix is **Generar claves** (which drops that database's devices); keys from before the stamp existed are claimed only when `ENVIRONMENT=production`. It needs HTTPS. Nobody is subscribed automatically (browsers require a click and a permission per device): the app offers it once after login, and each user chooses for themselves, from their profile (**Ajustes → Notificaciones**, the devices card under the table of notices), which of their devices get notifications and whether each also gets the group ones; on iPhone/iPad the app must be added to the home screen first (iOS 16.4+).

- What goes to the Telegram group is also pushed to every device that has group notices on (a per-device switch); private notices (a forgotten timer, the weekly summary) go only to that user's devices.
- **Notificaciones → Redactar aviso** in the admin panel is a composer: title (80 characters) and message (240), with a live preview. Each notice goes through **one channel at a time**, chosen in the composer: the **app** (push: where a tap opens, an optional https image, to your own devices to try it, to one user, to the devices that want group notices or to every subscribed device) or **Telegram** (`POST /manage/telegram/announce`: to your own private chat, to one user's, or to the group; the title in bold, no link or image). Sending to a group or to everybody asks for confirmation. Plain text only; the image shows on Android and desktop, not on iPhone/iPad. These manual notices ignore the general notifications switch, like the test message. The **Avisos en la app** card of **Notificaciones → Ajustes** shows how many devices and users are subscribed.
- **Timer notification**: while you have a timer running, every subscribed device of yours shows a pinned, silent notification with the game and the time played, shown when the timer starts (its periodic refresh is switched off for now, and so is the interval setting in the profile). Tapping it, or its **Parar** button, opens the app, where you stop the timer (no button on iPhone/iPad). When the timer stops, from wherever, the notification turns into "Timer parado · 1h 25min". On iPhone/iPad it is refreshed but not pinned. It follows the general notifications switch and, for now, there is no per-device switch for it.
- **Where a tap opens**: every notice opens the [notification inbox](#notification-inbox) (`#/notifications`), except the timer's own (it opens the home page, where the timer is), the recap's (its story), a started game's (that game's page) and an admin's notice with another link chosen in the composer (Avisos by default).
- Expired devices are removed automatically. Regenerating the keys unsubscribes every device.
- The pushed text is the same message as Telegram's without Markdown, cut to a title and a short body; how long messages and images fit is pending (see [roadmap.md](roadmap.md)).

## Notification inbox

A page of the app (**Avisos**, `#/notifications`, opened from the bell of the top bar, which shows an unread badge; it is not in the side menu) keeps what the group and the player were told, for whoever missed a push, has push off or saw it cut. It works with no device and no Telegram id: it is independent of both channels.

- **What goes in** (`utils/inbox.py`, called by `my_utils.send_message` and `send_message_to_user`): every group notice (one row for **each active player**, whether or not they follow it by push) and every private notice (that player only: the weekly summary, a wished game coming out, the achievements of a hidden unlock). A hidden achievement therefore reaches the group as "<name> ha desbloqueado un logro oculto" and its owner as the real message. Notices written by an admin in **Redactar aviso** go in too, by the audience chosen (the group and everybody mean every active player).
- **What does not**: the timer's own notices (start, stop, the forgotten-timer reminder: `in_inbox=False`), anything sent silently (an admin's edits) and anything while the general notifications switch is off. A player's own test message to their Telegram is not a notice either.
- **Links to games.** On Telegram a notice that names a game links it: a **new game** and the **wishlist** notices (release day and eve) to its RAWG page (`https://rawg.io/games/<slug>`; a game with no slug is only named), a **completed game** and the **recommended game** to its page in the app (`PUBLIC_URL/#/game/<id>`; with no `PUBLIC_URL` they are only named). Rankings, achievements and the timer's own notices carry none. A push cannot hold a link in its text, so it shows the name as plain text; the inbox keeps those game links in the body (`utils/inbox.linked_body`, `[name](url)`; the ones that do not fit the 255 characters go back to plain text, the last first) and the page shows them as links styled like the rest of the app's game links, RAWG's in a new tab. A card with links in it opens its page when tapped outside them. The AI prompts for these notices ask to keep the link as it comes.
- Each notice is stored as the push shows it (title, short body, and the page a tap opens), so the text does not depend on Telegram's Markdown. It is **a record, not a derived value**: unlike totals and rankings it cannot be recomputed, which is why it is stored.
- **Reading and deleting** (`/notifications`, always the caller's own): opening the page marks everything as read (the unread ones stay highlighted until the next visit); a notice is deleted with its ×, all of them with **Vaciar todo** (second click confirms). Nothing is shared: deleting yours leaves everyone else's.
- **Purge**: the daily 04:00 job `inbox_purge` deletes what is older than `inbox.retention_days` (14 by default, 1-365, edited in **Notificaciones → Envíos → Avisos en la app**).

## Adding a game

Anyone can add a game to the shared catalogue from the game picker ("Nuevo timer" and "Sesión manual"). The picker searches RAWG: the candidate the player chooses is created from its RAWG entry (`rawg_id`). **¿No aparece? Crearlo a mano** creates a game RAWG does not have: only the name is required (it is all a session needs), the release date and developer are optional, and the rest (cover, genres, Steam id) can be edited later from **Catálogo → Juegos**. A game made by hand has no `rawg_id`, so the RAWG sync reports it as pending (`ambiguous`/`not_found`) and never changes it. The API never picks "the best RAWG match" for a name: `POST /games/` without `rawg_id` always creates the game as typed. Duplicates are refused by `rawg_id` or by name (case-insensitive).

**DLCs and expansions.** `games.is_dlc` marks a DLC / expansion / edition and `games.parent_game_id` (a foreign key to `games.id`, ON DELETE SET NULL) is its base game, **optional**: a DLC can exist without one. RAWG lists them as games with a base game (`parents_count > 0`, base in `/games/{id}/parent-games`); the search results do not say so. A game created from RAWG gets the mark from its details (one extra request, only for a DLC) and brings its base game along: `crud/games._ensure_parent` links the base if the catalogue has it (by `rawg_id`) and adds it if not (best effort, one level; if RAWG fails the DLC is stored marked and unlinked, and a game is never created without RAWG details). **¿No aparece? Crearlo a mano** has an *Es un DLC o una expansión* check and, under it, an optional search of the catalogue for the base game (`POST /games/` with `is_dlc` / `parent_game_id`; a base that is not in the catalogue is a 400, and naming a base makes the game a DLC). The RAWG sync / resync only ever **adds** the mark and links the base when it is already in the catalogue (`rawg_sync._apply`; it never adds games, never unmarks, and replaces a link only on `overwrite`); a game synced before this existed is marked the next time it is processed, it is not a reason to be pending. **Catálogo → Juegos → Editar** changes every column of the game, `is_dlc` and the base game included (`PATCH /manage/games/{id}`: the base must exist and must not lead back to the game, naming one marks the game, and unmarking it drops the base). The picker's confirmation step asks `GET /games/rawg-parent/{rawg_id}` and, for a DLC, only **informs** ("Es un DLC o expansión de X, que se añadirá también…"): it never blocks. The game page and the Juegos cards show a *DLC* tag (`is_dlc`), and the page links to the base game when it has one. The game page also links to the game's RAWG page (`https://rawg.io/games/<slug>`, in a new tab, when it has a slug), where the trailer and the full information are: the app embeds no video. Stats are untouched: a DLC is a game like any other.

**Catálogo → Juegos** has a *Datos de RAWG* filter: *Incompletos* lists exactly the games the RAWG sync would try (no `rawg_id`, or the slug, cover or genres blank, or the tags never asked: `rawg_sync.pending_condition`), and *Sin ID de RAWG* the ones with no `rawg_id` (the link in the admin home goes there). A game leaves the list when it is complete, so it is the quickest way to see what is left to fix by hand after a sync.

## Average times and the debt ranking

`games.avg_time` is the average time to complete a game: the **main story of HowLongToBeat** (`comp_main`), in **seconds**. It is filled in when a game is created from RAWG and when somebody completes it, always from a *clear* match by name (`utils/hltb_sync.py`, `pick`): the name has to be the same ignoring case, accents, punctuation, a leading "The" and roman numerals (Hades II is Hades 2), or very close (90 %) and clearly ahead of the next result, and the numbers in the two names have to agree (a sequel is not the game). A name that is the other with words added in front also counts ("UFC 5" is "EA Sports UFC 5"), when it is the only one and the numbers agree; words added at the end do not (Doom is not Doom Eternal). DLCs, mods and ROM hacks never match; every other type of HowLongToBeat entry is a game (online-only "multi" and "endless" ones included). Two exact names are told apart by the release year, then by being a plain game. The search is given the name with plain quotes and with colons and slashes as spaces, which is what HowLongToBeat answers to. A doubtful match leaves the stored time alone.

**Catálogo → Juegos → Sincronizar tiempos (HLTB)…** (next to the RAWG sync) goes through the games you choose and **replaces** their time with HowLongToBeat's, even one edited by hand: HLTB is the source of truth. Each game takes about 5 s, so the window asks **which games** (and shows how many it is and how long it takes before you accept): **all** of them, **only the ones with no time** (none stored, or 0: nothing else is touched), **only the ones whose time is not believable** (more than 1,000 hours, which is where a time stored 3600 times too big ends up) or **the N played most recently** by anybody (a number of your choice, 50 by default; a game nobody has played is never among them). It goes through them most played first, or most recent first for the recent ones (`scope` and `limit` of `POST /manage/hltb-sync/start` and of the estimate). It asks for the phrase `SINCRONIZAR`, runs in the background with a progress window (refreshed every 2 s, with an estimate of the time left; each game takes about 5 s because HLTB's search makes several requests, so the whole catalogue is a matter of tens of minutes; a list of doubtful games that is open while it runs is not redrawn, but the figures keep moving) and can be cancelled, and it stops after 5 failed requests in a row. When it ends it lists what it did not touch: *ambiguos* (with the candidates and their hours, to type the time by hand in **Juegos → Editar**, in seconds), *sin resultado*, *sin tiempo* (found, but HLTB has no main story time) and *errores*. A game without a time there keeps the one it has.

**Catálogo → Juegos → ⋯ → Resincronizar (RAWG y HLTB)…** refreshes **one** game from both sources at once (`POST /manage/games/{id}/resync`, after a plain confirmation: no phrase, it is a single game). RAWG goes first: every field it gives (date, developer, image, genres, tags, Steam id) **overwrites** the stored one, but a blank never does and the name is never touched (1 to 3 calls; a game with no `rawg_id` is searched by name first). Then HLTB replaces the average time exactly like the bulk sync. A doubtful match changes nothing: the dialog lists the RAWG candidates to pick one right there (`/manage/rawg-sync/apply`) and the HLTB ones with their hours, to type by hand. Each source reports on its own, so one failing (no key, quota, HLTB down) does not stop the other.

**Debt** is how much a player still has to play, by those averages: for each game they have started and not finished, `max(0, average - time played)`, added up. A game counts only if the player has at least one session of 10 minutes or more in it, it has an average time, and it is neither completed nor abandoned (a game completed on any platform, or with every library entry abandoned and not played since, is left out). There are two debts: `debt` of a season (`?season=`, the running one by default) and `debt_total` over every season, where a game completed in any season is not owed. `GET /statistics/rankings?ranking=debt,debt_total` answers `debt_time` (seconds) and `games` (the ones that still owe time) for every player, the most indebted first (`crud/debt.py`); nothing is stored. The bot has **Deuda** and **Deuda total** in its rankings menu. The app shows it once the Estadísticas page has its rankings.

## Recap (Wrapped)

`GET /statistics/recap/{period}` answers the recap of a **month** (`2026-09`) or a **season** (`2026`): they are the same computation over a different range (`crud/recap.py`), so the yearly recap of [#111](https://github.com/la-viciacion/la-viciacion/issues/111) reuses it. Nothing is stored. The `group` part (hours and sessions, the ranking with the previous period beside each player, the most played games, the busiest day, achievements earned and the rarest one) is readable by any logged-in user; `?username=` adds the `player` part (hours against the previous period, position, star game, best day, best streak, games started and completed, achievements, rarest achievement and the usual playmate), which is only for that player or an admin. A session counts in the period and the day it started in; the playmate is who the player spent most time with in the same game at the same time. Both parts also carry when it was played (`by_weekday`, Monday first, `by_hour` and `by_day`, by the weekday, hour and day each session started in) and the genres with the most time (`genres`, top 5; a game of several genres counts in each), and the player part their top 5 games with cover (`top_games`). The group part leaves out secret achievements; the player's own recap keeps theirs. A period still running answers what there is so far (`complete: false`); a future one is refused with 400. The emergency account never counts.

**The page** is `#/recap[/<period>[/<username>]]` (no menu entry: it is reached from the profile's card, the in-app bar and the notice's link, and only **for a few days**: see *Availability* below): with no period in the address it opens on the month that has just ended and the address stays `#/recap` (the same for `#/story`; a period in the address, or one chosen on the page, is the one shown and goes into the address), the period is chosen as Mensual or Anual, a year (since 2023) and, for a month, the month (never a list that grows every month; the same pickers are in the admin tab); **only a finished month or a finished season can be chosen** (the running month, and the running season in Anual mode, are not in their lists, and an address still naming the running month falls back to the one before); a season still running is also **locked** (for an admin too, so they see what a player sees), by address too — `GET /statistics/recap/{period}` refuses it (`RECAP_SEASON_LOCKED`, `crud.recap.season_locked`) until it is unlocked for exactly that year (`annual.unlocked_year` in `app_settings`; it locks itself again the moment that year stops being the running one, so nothing needs resetting by hand). The admin panel's own links lift it (below); everybody else only once it is unlocked — by hand, in **Notificaciones → Envíos**, or on its own the instant its notice reaches the group (`utils.recap_notices.announce_recap`), so the December link in that notice (below) is never dead on arrival, and nobody can watch the season change day by day before that. It opens on the player's own recap, with the button "Ver mi historia" first; the group's recap is a quieter second tab. An admin can add a player's username to the address to see theirs. **The story** is `#/story[/<period>[/<username>]]` (button "Ver como historia" on the page): the same recap as full-screen slides, like a music app's year in review. A phone gets the whole screen and a wide screen a 9:16 card; tap the right or left side (or use ← → and space, or the arrows beside the card on a wide screen) to move, hold to pause, swipe, Esc or × to leave. It tells the hours against the previous period, the star game and top 5 games with covers, the busiest day (with a grid of the month), the favourite weekday, the part of the day, the genres, the streak, the usual playmate, the library and achievements, and the group's hours and podium; a slide without its figures is left out (`lib/story.js`). Each slide can be shared as a 1080x1920 PNG made with a canvas (`ui/story-image.js`: the share sheet on a phone, a download elsewhere; covers that do not allow it are left out of the picture). **Availability.** A player can open a finished recap only in the first days after it: the month that ended during the 1st to the 5th (`WINDOW_DAYS`, `crud.recap.recap_closed`) and, in January, also the season that ended. Outside that window `GET /statistics/recap/{period}` answers 400 (`RECAP_CLOSED`), by address too, so an old link no longer opens it. The same holds for an admin, so with their own account they see what a player sees; the links of the admin panel (**Probar resumen**) name the player in the address (`#/recap/<period>/<username>`, also their own), which the pages send as `unrestricted=true` and which only an admin can use: it lifts both limits, shows the pickers and is how the panel looks at any period. The setting `recap.always_available` (admin panel: Notificaciones → Envíos → Acceso a los resúmenes, off by default) lifts the window for everybody; there is still no menu entry for it. **The page's pickers** (type, year, month) are drawn only while that setting is on, for an admin too (`GET /statistics/recap-access` → `selectable`), or when an admin's address names a player (the panel's links); otherwise the page shows just the period it was opened on, and any other address answers `RECAP_CLOSED`. The running season keeps its own lock (`annual.unlocked_year`). **The first days of the month** (1st to 5th, `WINDOW_DAYS` in `lib/recap-window.js`), the recap of the month that ended is also offered inside the app, for whoever has no push on: a bar at the top when the app opens (only if the player played that month) that goes away for good once it is opened or closed, and a card in the profile's Resumen tab that stays for the five days (with `recap.always_available` on, the card is there every day, for the month that ended; its **Ver datos** opens the page with the pickers). In January there are two periods on offer, the season that ended and December: the bar offers the season first (and December the next time the app opens), and the profile shows a card for each. What this device has already shown is remembered in `localStorage` (`lv-recap-seen-<period>`), not on the server, so another device may show it once more; opening your own story also clears it. **The notice** is one short message, the same on both channels: "Ya está disponible el resumen mensual" (or "anual"; it goes to the group, so it does not speak to anybody, and it does not name the period) with the link to the story (for the monthly one, `#/story` with no period: the story opens on the month that ended; the annual one links `#/story/<year>`, since a bare story would open on a month), in the Telegram group and as a push on the app's devices that have group notices on (a tap opens the story, also when the app is already open: the service worker takes that window to the page). It carries no figures and nobody is written to in private: the numbers are in the page and the story, and the AI does not word it. Nobody gets it for a period in which nobody played. **The monthly notice** is the job `monthly_recap` of the scheduler: on the configured day (1 to 5, the days the app also offers it; 1 by default) and time (10:00) it announces the month that ended. **The annual notice** is a separate job, `annual_recap`, over the season: in **December** (day 20 to 28; the season so far) or in **January** (day 1 to 5; the season that ended), as configured (`annual.month`, `annual.day`, `annual.time`; the month and the day are checked together when saved, so a day that does not fit the month is refused). Its push has its own tag (it carries the period), so it does not replace the monthly one. Both jobs are **off by default** (`monthly.enabled`, `annual.enabled`) and, if the server is off at the slot, run when it returns within 12 hours. They are set, and tried, in the admin tab **Notificaciones → Probar resumen** (to try it) and **Notificaciones → Envíos** (to schedule it): any month or season for any player (the page and the story), the notice as it would go out (`GET /manage/recap/preview?period=`, nothing is sent), sending it now to the admin alone (their own Telegram chat and devices) or to the group (`POST /manage/recap/send`, the same code as the jobs) and, under **Envío automático**, the schedules of both. In-app, the season is offered only in the first days of January, whatever month the annual notice is set to.

## Platform catalogue

**Catálogo → Plataformas** in the admin panel manages the platform catalogue used by sessions and library entries: add one (its id is made from the name and never changes), rename it (everything that uses it follows), and delete one that nothing uses (a platform that still has sessions or library entries is refused and the message says how many). **Sesiones** and **Biblioteca** next to a platform jump to those rows.

## Revoking achievements

The pictures of the achievements come from the files of `api/achievement_images/`, which the API loads at every start (see [architecture.md](architecture.md)); a picture uploaded by hand from **Catálogo → Logros → Imagen…** is replaced at the next start if that achievement has a file there, so to change one for good, replace its file.

In the admin panel, **Catálogo → Logros**: pressing an achievement lists who has unlocked it and when. **Editar** changes the date it was obtained (its year is the season) and **Revocar** removes it without announcing anything. Achievements are re-evaluated on every check (after each stopped timer and after a change to the sessions or the library), so if the player still meets the condition it will be unlocked again: correct the data that triggered it first (e.g. a wrong session).

**Recalcular logros…** (the toolbar of **Logros**) works out again every achievement of every season from the sessions and the library, with the same rules as the live checks (`Achievements` in `collected` mode, `crud/achievements_recalc.py`), and brings what is stored to that: it **adds** what is missing, **corrects** the date or the game of what differs (a date edited by hand is calculated again) and **revokes** what no longer holds or is repeated. Everybody counts, active or not, never the emergency account, and the players, the seasons and the achievements to work out can be chosen (all by default, the switched-off ones always left alone: `user_ids`, `season_list` and `achievement_keys` in the API). **It never notifies anybody**, by construction: it does not go through the announcements at all. It takes two steps: a preview (every change can be unticked; the API's `accepted` holds the `ref` of the ticked ones, and nothing else is made) that lists exactly what it would add, correct and revoke (`GET /manage/recalculate-achievements/preview`, which changes nothing) and, after typing `RECALCULAR`, the recalculation itself in the background (`POST /manage/recalculate-achievements`; it works everything out again when it runs). Two achievements cannot be told apart from the sessions alone and are worked out in an approximate way: **Lo he abierto sin querer** from the earliest session of 5 minutes or less (a manual one cannot be told from a real timer) and **Trabajo en equipo** from sessions of 4 or more different players that overlap (a forgotten timer counts as playing). **Justo a tiempo** is judged when the game is completed, against the average time HLTB gave then. **Recalcular logros…** judges it again from the library (the time of each completion's run against the `avg_time` stored in `games`, dated the completion; it never asks HLTB nor changes that time), and since the average may have changed since, every change of its preview can be unticked, the revocations of this one coming unticked, and each of its lines shows the time of the run against the average (difference, % and allowed margin, for the game it has and the one it would get). One already stored that still holds is never moved to an earlier completion that also holds: it is only corrected when it no longer does. The recalculation that follows a player's own session never touches it. The recalculation that follows a player's own session announces only what it adds dated on or after the first day that session touches (the earlier of the old and the new start when it is edited); what it finds from before, which the session did not cause, is stored in silence.

**Creating, editing or deleting a session of your own** (the season of the session, and the one it left if it moved to another), and **anything an admin creates, edits or deletes in a player's sessions or library** (**Jugadores → Sesiones** and **Biblioteca**), does the same recalculation for that player and the seasons involved: what it earned and no longer holds is revoked, and dates that moved are corrected, including dates edited by hand. It is silent for an admin's changes; for a player's own sessions it also **announces what the change adds** (a hidden one as the hidden notice to the group and the whole message privately), but never a revocation, a corrected date, or the two that need several players at once (teamwork and "Todos a una"), which only a timer that starts announces. Because it works everything out again, an achievement that was missing before and is found now is announced too. The other players' achievements are not touched (a teamwork that depended on a deleted session stays for them until the next **Recalcular logros**).

## Manual sessions

From the home page a user can add a finished session by hand (**+ Sesión manual**: game, platform, start, end; before it is saved the form says how much time it adds, "Vas a añadir 1 h 30 min a «Doom»", and asks to confirm; changing a field asks again) and correct or delete one of their own from **Perfil → Resumen → Juegos → Sesiones** (the sessions of that game and season; **Editar**, only for the current season). Cancelling a timer or deleting, or moving to another game, platform or season, the only session of a game leaves its library entry empty, and the empty entry goes (`users.drop_empty_entry`) only if that session made it: it began that same day, and it is not completed or abandoned, the player has not rated the game and no price they noted lives in it. An entry the player added by hand on an earlier day stays, so a timer started and cancelled by mistake never takes a backlog game away. In the home list of latest games, pressing a game's row unfolds its latest sessions (**Editar**, **Ver todas**), the complete mark (an empty circle in soft white, with no box, while the game is not completed this season; a filled green circle once it is) opens a window to mark it as completed (once per game and season, announced to the group; the window is the confirmation, so its **Marcar completado** completes with one press) and the play button starts a new timer. The API (`POST /timers/manual`, `PATCH`/`DELETE /timers/{id}`) enforces: the end after the start and not in the future, at most 24 h, **current season only** (closed seasons are frozen; admins can still edit them), and no overlap with any other session of that user. **A manual session is refused (409) while the user has a running timer**, whatever the times: they stop or cancel the timer first (the **+ Sesión manual** button is disabled while a timer runs). Completions follow the same rule: a game is completed only in the current season, and once its season is closed the completion is frozen too (**Cambiar fecha** and **Desmarcar** disappear and `PATCH /users/{username}/library/{id}/completion` answers 409). **Ratings:** a player can rate any game of their library from 1 to 100 (whole numbers), once per game whatever the seasons or platforms they played it on (table `game_scores`; sessions have no rating). It is offered right after completing a game in the profile, in a question (**¿Quieres puntuarlo?**, with **Ahora no**) that opens when a completion is confirmed in the home history and, at any time, with **Puntuar** / **Cambiar nota** on every row of the games list of the profile, where all the entries of the game show the same rating. **A game played on several platforms in a season is one row of the library, not one per platform**: `GET /users/{username}/library` groups the entries of a game and season and answers one item for them (`platforms` lists every platform, most recent first), standing for them with the completed entry if there is one, otherwise the most recent. The time and the sessions of a row were already those of the game and season, so nothing is lost; the buttons act on that entry, and the platform filter matches any of the platforms. The entries themselves (one per game, platform and season) are unchanged, and so are the rules that use them. **Perfil → Mis juegos** (between Resumen and Ajustes) lists the whole library of the player, every season, with the same row buttons as the summary list, filters (name, season, state, rated or not, platform) and **Puntuar al azar**, which opens a window with a random game of those still without a rating: it asks for the rating, **Omitir, ver otro** shows another one, and **Dejar de puntuar** closes it; each saved rating brings the next game by itself until none is left. A rated game shows its rating next to its name wherever the player's own games appear (the home history and timer card, the completion window, the most played games and the games list of the profile) as a small ring whose colour goes from red to green with the score. The admin panel (**Jugadores → Puntuaciones**) can create, change and delete any rating; deleting a user or a game removes theirs after the usual confirmation. Ratings of the others weigh a little in the recommendations (see below). A player cannot change the game of an existing session: they delete it and add it again. An admin can: **Jugadores → Sesiones → Editar → Juego** (a session logged on the wrong game); the session moves to the right game, which gets its library entry for that platform and season if it lacked one, and the old entry is removed when nothing is left in it (no session; one with a completion stays). The same follow-up applies when an admin changes a session's platform or start date. Manual changes check the user's achievements silently (nothing is announced to the group), and creating one also creates the library entry for that game/platform/season if it is missing.

## Abandoned games

A game of the running season that you are not going to finish can be marked as **abandoned**: in **Perfil → Resumen → Juegos**, its row has an **Abandonar** button, which asks "¿Seguro? Pulsa otra vez" like **Marcar completado** (and **Retomar** to take it back, with the same confirmation); on a phone, like the other buttons of the row, it shows only its icon. The row then shows an **Abandonado** tag instead of "En curso". It is reversible and silent (nothing is announced), and **playing the game again resumes it by itself** (a session starting after the mark), so there is nothing to undo. A completed game cannot be abandoned, completing an abandoned one just completes it, and, like completions, only the running season can be changed (a closed season keeps what it had). It is a note for the player: totals, rankings, streaks, achievements and recommendations do not change. An admin sees and can edit the raw mark in **Jugadores → Biblioteca** (**Abandonado el**).

## Prices and cost per hour

A player can note **what they paid for a game, on each platform** they have it on (a game bought on PC and on Switch is two purchases). Only the price is stored, in `users_game_prices` (migration 045): `user_id`, `game_id`, `platform` (one of the platforms of the player's entries for that game) and `amount_cents` (euros as cents, from 0, a free game, to 10,000 euros; one currency, the euro), unique per player, game and platform. It is **not** a column of `users_games` because that table has a row per platform *and season* (the price would be repeated in every season and lost with an entry an admin deletes) and only has a row once the game was played. Deleting the player or the game deletes their prices; a platform with prices cannot be deleted (the panel counts them as `precios`).

- **Noting it**: in **Mis juegos** every row has a **Precio** button that opens one box per platform of the game (an empty box takes the price off; only what changed is sent, `PUT /users/{username}/games/{game_id}/price` with `{platform, amount}`, `amount` in euros with a point or a comma, or `null`). The library items (`GET /users/{username}/library`) carry `price_cents` on each of their `platforms`, and a row says "Pagado: 24,99 €".
- **Your summary** (`GET /users/{username}/value`, the card **Lo que has gastado** above the list): what you have spent, how many games have a price, the mean cost per hour and your five cheapest and dearest per hour. The cost per hour of a game is **everything paid for it over all the hours the player has played it** (every platform, every season) and only exists from **half an hour** of play (`MIN_SECONDS`); a game played less counts as spent and has no cost per hour.
- **The group** (`GET /group/value`, the **Rentabilidad** section of **Biblioteca del grupo**, and `cost_per_hour` of the game's overview, a figure on the game page): the **mean cost per hour of a game** (the sum of what the contributors paid over the sum of their hours), shown **only when at least three players contribute to it** (`MIN_CONTRIBUTORS`; a contributor has a price for the game and at least half an hour played). The answer **never has a player or a price in it**: the hours of each player in a game are public, so the cost per hour of one player would give their price away, and with fewer than three contributors the mean would give away the others'. The emergency account never counts.
- **Who reads a price**: the player and an administrator (like the rest of their data: `ensure_self_or_admin`); nobody else, so another player's library, which carries the prices, is refused. The admin panel has no field for them. The prices are in the **database dump** like everything else, which is unavoidable. The **chat**, the **bot**, the recaps and the notices never use them.
- **In the export** (below) the prices of the player go in a `prices` list (`game_id`, `platform`, `amount_cents`) and the import accepts it: a price is only added for a game the player has on that platform (after the library of the same file is imported), one already there is kept, and the report counts them as `prices`.

## Exporting and importing your data

**Perfil → Ajustes → Tus datos** has **Descargar mis datos**, a `.json` file (`laviciacion-<usuario>-<fecha>.json`, `GET /users/{username}/export`) with what is yours: finished sessions, library entries (with their completions and abandoned marks), ratings, the prices you noted, wishlist and the achievements you hold, plus the games and platforms those rows mention so the file means something on its own. It has no email, no Telegram id and nothing derived (totals, rankings, streaks, the time of an entry); a running timer is not in it.

**Importar datos…** is **switched off in the profile for now** (`IMPORT_ENABLED` in `front/js/pages/profile/data.js` hides it, and `IMPORT_ENABLED` in `api/src/routers/users.py` makes `POST /users/{username}/import` answer 404; the code stays). It takes such a file back (`POST /users/{username}/import`, yours or an admin's) and first shows what it would do (`?dry_run=true`: how many sessions, games, ratings and wishes are new, how many you already have, which cannot be imported and why) before asking for a yes. It is a **merge that never overwrites**: whatever the account already has wins, so importing the same file twice changes nothing; it follows the app's rules instead of bending them:

- sessions need the end after the start, not in the future, and no overlap with anything else you played (the first one wins); the duration is recomputed from the times; a session already there (same game and start) is counted, not added; each session opens the library entry it needs
- a player imports **the running season only**: rows of a closed season are reported and skipped (an admin imports any season, as with manual sessions)
- games and platforms are shared catalogues: a row whose game (looked up by id, then by name) or platform does not exist here is skipped and named in the report. An **admin's import** creates the missing games and platforms instead, which is how a file from another installation is brought in
- a completion keeps its date but stays one per game and season; ratings only for games you have (after the import) and the wishlist only for games you do not
- **achievements are not imported**: they are earned. After an import with new sessions the check runs silently in the background and awards the ones the sessions deserve
- the file is bounded (50,000 sessions, 8 MB through the proxy) and validated; one malformed row refuses the whole file before anything is written

The same panel section also offers the admin's full database copy, see [deployment.md](deployment.md#backups-and-restore).

## Audit log

**Sistema → Registro** in the admin panel lists what the admins have changed from the panel, newest first: when, who, a sentence ("Editó sesión #12", "Borró juego #hades", "Cambió los ajustes") and a **Ver** that unfolds how the row was before and what was sent. It can be filtered by admin, by section and by kind of action (create, edit, settings, delete). Only changes that went through are listed, secrets (passwords, tokens, API keys) never appear in it, and it does not record what players do on their own account except what matters for security: the same list shows, for every account, logins and failed logins (and when one locks the account for a few minutes), password changes and recoveries, a change of one's own email or Telegram id and a refused access to the panel, each with the address and browser it came from, and **every time the AI provider refuses a call for lack of quota** (see AI-written notices). The filter **Tipo** tells the panel's changes from these. The log is read-only and is never edited or deleted from the panel. Technical details in [architecture.md](architecture.md#audit-log).

It lists **Principal** (Inicio, Actividad), **Explorar** (what is about the whole group: Juegos, Calendario, Logros, Jugadores and Estadísticas, marked WIP: a placeholder until the statistics are ready), **Tú** (what is about the player, even when it also shows the others: Mi perfil, Deseados, Recomendados, Retos, Ajustes), **Administración** (admins only) and, at the foot, **Cerrar sesión**. ## Players pages

**Jugadores** (menu → Explorar, `#/players`) lists every player of the group: photo, name, total hours, games, completed and either what they are playing now (green aura) or when they played last; the ones playing come first, then the latest to play. Pressing one opens **their page**, `#/player/<id>`, with what is public: the figures of a season or of all of them (the same pills as the profile), most played games with their ratings, latest achievements and what they play now. It never shows the email, the Telegram id or the settings, and the library only as the **comparison with yours** (below), never as a list of its own; a player who hides "playing now" (Ajustes) still appears, only without the live status. **Tu biblioteca y la de <jugador>** (`GET /group/players/{id}/compare`, `crud/library_compare.py`, derived; a player cannot compare with themselves and the emergency account is not a player): on another player's page, the games **you both have** (with the hours, whether it was completed and the rating of each), **only yours** and **only theirs**, each list from the most played, eight games at a time with **Mostrar más**, plus the same affinity. A game counts once however many seasons or platforms it was played on. It is readable by any logged-in user on purpose: it is what each game's page already says (who has it, with their hours and rating), grouped by pair of players. **Afinidad contigo**: on another player's page (nothing on your own) a percentage says how alike your taste and theirs are, from both libraries, ratings and time played per genre over every season, whatever the season on screen. Three parts: the games in both libraries over the games in either (weight 50 %), how close the ratings are on the games both rated (30 %) and how much of the time played goes to the same genres (20 %). A part that cannot be worked out (no game rated by both, nobody played) leaves the total and the others weigh what is left. With fewer than 3 games in both libraries the page says there is too little data instead (`crud/affinity.py`, the `affinity` field of `GET /group/players/{id}`). Inactive players count like the rest. `GET /group/players` and `GET /group/players/{id}?season=`, derived; nothing is stored. Inactive players (who cannot log in or act) are listed and counted like the rest, marked with an "Inactivo" badge and a dimmed card (also on the player page and in the list of players of a game), with a Todos / Activos filter on the page; never the emergency account. Still left out of notices (push, Telegram, wishlist) and of who is playing now.

A session counts for a played day, a streak or the games of a day only when it lasts 10 minutes or more; hours add up whatever the length of each session. The texts, in Spanish, are in `api/src/utils/achievements.py` and then in the database (editable in the panel).

Teamwork and "Todos a una" only count timers (never manual sessions) while they happen, and a forgotten timer still counts as playing. **Recalcular logros** works them out from the overlapping sessions instead.

**The world outside the app.** Fifteen achievements that depend on when and what was played, not on how much. All of them are hidden (secret), have no season limit (earned once in a lifetime) and begin to count in 2027 (`since`; only what was played from that season on counts, and nothing is awarded or announced before it), like any other, so the admin panel can change that. They are about the moment a timer **starts**, and they are judged right then (the same moment as early riser or the release day), whatever it ends up lasting: the 10-minute rule of the days and streaks does not apply, and a session that starts on one day and ends on the next belongs to the day it started. The general check (after a stopped timer or a change to the sessions, and **Recalcular logros**) judges the finished sessions by their start in the same way, so a manual session counts too and what a recalculation finds agrees with what a timer earned. **Nothing is stored for them but the award**: the days, the sky and the weather are worked out when asked (the weather is the one thing that comes from outside, see below).

- **The calendar** (`utils/external_events.py`): *Que la Fuerza te acompañe*, a timer started on the 4th of May with a Star Wars game (by its name, which has to say Star Wars or one of a few titles that do not, such as Jedi, Sith, Skywalker, Mandalorian, Old Republic, TIE Fighter, X-Wing or Battlefront, or by RAWG's tag "Star Wars"); *Mario Day*, the 10th of March with a game whose name has the word Mario (Super Mario, Mario Kart, Paper Mario, Dr. Mario...); *Un día que no existe*, the 29th of February (the first possible one is 2028); *Cumpleaños feliz*, the player's birthday (only if they entered their birth date; a 29th of February is celebrated on the 28th the years that have none). The two with a game name it in the notice.
- **The sky** (`utils/astronomy.py`, no API: Jean Meeus's formulas, accurate to a couple of minutes, the day is the server's local one): *Luna llena*, a day with a full moon; *Eclipse lunar* and *Eclipse solar*, the day of an eclipse **seen from the player's city** (they need to have chosen one; without it they cannot be earned): a solar one has to cover at least 0.25 of the Sun's diameter there with the Sun above the horizon (`astronomy.SOLAR_MIN_MAGNITUDE`; about 8 in 14 years from Madrid), a lunar one has to enter the umbra by at least 0.1 (global magnitude, so a barely noticeable bite does not count; `LUNAR_MIN_UMBRAL`) with the Moon above the horizon at its greatest (about 10 in 14 years from Madrid), and the timer has to start **in that night, after the sunset** at the player's city (from the sunset before the eclipse to the next sunrise, so one started at 1:00 after the eclipse's evening counts and one started at noon does not; the achievement is dated the day the timer started). The positions come from the `ephem` library, which carries its own tables (nothing is downloaded); and one achievement for each of the two equinoxes and the two solstices.
- **The age of a game**: *De la misma quinta*, a timer on a game that came out the year the player was born (it needs their birth date and the game's release date from RAWG); *Arqueólogo*, a timer on a game that was 25 years old or more the day it started (`external_events.ARCHAEOLOGIST_YEARS`; a game with no release date from RAWG never counts, so a wrong date there gives a wrong result).
- **The weather** (`utils/weather.py`, [Open-Meteo](https://open-meteo.com), free, no key): *Jugando bajo la tormenta*, a timer that starts in an hour with a thunderstorm (WMO codes 95, 96, 99) at the player's city, and *Niebla en Silent Hill*, one that starts in an hour with fog (45, 48) on a **horror** game. A game is a horror game when its RAWG tags say it (`games.tags`: RAWG has no Horror genre, only tags such as Horror or Survival Horror; the tags are filled in when a game is created and by the RAWG sync of the admin panel for the ones that have none; a game RAWG has no tags for is saved with an empty text, so the sync asks about it once and not on every run). They need the player's **city**, which they choose in **Perfil → Ajustes → Mis datos**, as one more field of the form with their name, email and Telegram ID, with nothing that says what it is for: they type a name, pick one of the answers of Open-Meteo's geocoding (`GET /users/places/search`) and what is saved is its name and the coordinates of its centre, never a GPS fix; nobody else sees it, and without a city these two are not earned. Each past day is asked for once (the forecast service for the last 80 days, the archive for older ones, whose storm data is less reliable) and kept in `weather_days` (outside data, not derived from the sessions, so it may be stored); today is asked for again each time. If Open-Meteo does not answer, nothing is decided at that moment and the next check tries again (no request is made for five minutes after a failure); **Recalcular logros** leaves the weather ones exactly as they are for a player whose weather could not be had, instead of revoking them. The birthday needs the **fecha de nacimiento** of the same section (only the player and the admins see it; changing it and recalculating moves or revokes the award).

**Nothing older than its start.** Every check that collects history reads only what happened from the season the achievement starts to count in (`since`): the sessions, the library entries and the completions of an earlier season are left out, in every family (hours, days, games, completions, the hours of a game, the dates, the sky, the weather and the games of the outside world, the rescues and the challenges). A test builds a whole year of history before the start and checks that none of them is earned (`LifetimeTests.test_nothing_older_than_the_season_each_one_starts_in_is_read`), so a new family has to respect it too.

**No season limit.** Most achievements are earned once a season. The ones whose key ends in **`_LIFETIME`** are the exception: they count the whole history of a player (the hours of a game, the days, the games, the completions of every season added up) and are earned **once in a lifetime**. Which they are is written in their name, in `utils/achievements.py` (`is_lifetime`), with a test that fails if a key and its table of thresholds do not agree: there is no switch to change it. They are other achievements than the seasonal ones (the seasonal 500 and 1000 hours in a game stay as they are), so they are created like any new one, switched off in an installation that has some, and the panel marks them **Único** (the **Logros** page too, once unlocked). While none is switched on their checks cost nothing. **Recalcular logros** works them out once per player, whatever seasons are chosen, keeps the oldest if one was earned twice and files each in the season of its date.

**Valid from a season.** Each achievement says the season it starts to count in (**Desde** in the panel, `valid_from_season`). Before it nobody earns it and nothing is announced about it, **Recalcular logros** leaves what is stored in those seasons exactly as it is (it neither adds nor revokes), and the **Logros** page shows it only as a hidden one ("Logro oculto", with nothing about it, not even when it will begin, but with its aura if it is special), secret or not, unless the player already has it, so it is simply there, unlocked by nobody, when its season arrives (a switched-off one is not listed at all). The ones that existed before this was recorded are valid from **2023**, the first season of the app; every achievement has it in its definition (`since` in `utils/achievements.py`; a test fails if one does not say it). **The rule for new ones: every achievement added from now on starts in 2027** (the season after the one it is written in), so it is not retroactive and nothing is awarded or announced before then; the 2023 ones are listed in the catalogue test (`LEGACY_2023`) and a new one that says another season fails it, so choosing a different season is a decision made on purpose there and in the definition. It can be changed from the panel at any time. For the ones with no season limit (`_LIFETIME`) it also marks where the history they count begins: **only what was done from that season on counts** (the hours of a game, the days, the games), and they are not earned at all before it.

**Active or switched off.** Each achievement has an **Activo** switch (admin panel, **Logros**). A switched-off one is not earned by anybody, nothing is announced about it, **Recalcular logros** leaves it exactly as it is (it neither adds, corrects nor revokes it) and the **Logros** page does not show it, not even as a hidden one, unless the player already has it. What was earned before it was switched off is kept. An achievement the code no longer has (it was dropped) is switched off by itself at startup and never deleted. Everything is on by default: a new achievement starts active, and the season it is valid from (below) is what keeps it from counting before its time. Switching one on does not look back: use **Recalcular logros** to award the past, choosing that achievement. **Secret achievements.** An admin can mark an achievement as **Secreto** (admin panel, **Logros**; none is by default). A secret one is **hidden from whoever has not unlocked it**: the **Logros** page shows a locked "Logro oculto" (no title, text or picture; the API sends only the id, `hidden: true`, its level and **who has it**, names only, with no date and no count of times, so it is seen that it can be earned), and the public player page and the activity feed say "logro oculto" for it too. When somebody unlocks one, the group (Telegram and push) is only told "<name(s)> ha desbloqueado un logro oculto" (who, not which) (with "Logro especial de nivel N" on top if it is special): no title, text, game or picture. The player gets the whole notice **privately**, on every channel they have (Telegram if they linked an account, push if they have a device), unless the notifications are off or the check is silent (the admin panel's recalculation never notifies). With several players at once (teamwork, "Todos a una") the group gets one message naming them and each gets their own. Whoever has it sees it in full with a "Secreto" tag and can see who else has it, like the rest. **Special achievements.** Independently of being secret, an achievement can be **Especial** at one of three levels (`achievements.special`, 0 = ordinary), and each level is a colour: **1 plateado, 2 dorado, 3 morado**. A special one shines with an **aura of its colour** (and a tag that says so) on the **Logros** page and in the lists of achievements of a profile, **whether it is unlocked or not**, so that everybody knows there are special ones to aim for: a locked special one is a locked card with only its aura. When somebody unlocks a special one that is not secret, the group is told the whole achievement with "Logro especial de nivel N" on top (and its picture), like any other; if it is secret too, it is told as a hidden one ("<name> ha desbloqueado un logro oculto") with the level on top (it says how rare it is and nothing about what it is), and the player's private notice has the whole message with the same first line. Secret and special are independent (`achievements.secret`, `achievements.special`): an achievement is hidden, special, both or neither.

**Which are special and which are secret.** The definition of each achievement in `utils/achievements.py` says it (`special`: 1 to 3, `secret`: true; neither when it says nothing), and an installation creates it like that; an admin can change either afterwards, and the database is the truth. A level reflects how hard or rare it is to earn: 1 silver is a clear effort or an uncommon coincidence, 2 gold is months of constancy or something very rare, 3 purple is nearly out of reach. The levels, by family: **in a day** 12 h (1) and 16 h (2); **in a game in a season** 100 h (1), 500 h (2) and 1000 h (3); **hours in a season** 500 (1) and 1000 (2); **games played** 42 and 50 (1) and 100 (2); **games completed** 25 (1), 42 (2) and 100 (3); **10 games in a day** (1); **days played** 200 (1), 300 (2) and 365 (3); **streaks** 100 and 200 (1), 300 (2) and 365 (3); **with no season limit** 1000 h in a game (2), days 1000 (1), 2000 (2) and 5000 (3), hours 2000 (1), 5000 (2) and 10000 (3), games played 500 (1) and 1000 (2), games completed 500 (2) and 1000 (3); **others** "Lo estaba esperando", "Semana laboral", "Salvado por la campana", "Justo a tiempo" and "Trabajo en equipo" (1), "Rescate" (2), "Remate" (3), "Cazarretos" (1), "Todoterreno" (2) and "Misión cumplida entre todos" (1); **the world outside the app** the storm, the 29th of February and "De la misma quinta" (1), the fog with a horror game (2) and the two eclipses (3). They are valid from 2027, and until then they are listed as hidden ones with that aura. Every special one is secret too. Marked as secret besides: "Media jornada, 12 horas", "Sesión de 4 horas", "La respuesta (de verdad)", "Indecisión x2", days played 200, 300 and 365, "Del tirón", "Trabajo en equipo", "Feliz año nuevo", "Salvado por la campana", "Madrugador", "Plus por nocturnidad", "Justo a tiempo" and every one about the world outside the app. Migration 029 gave the first set of values to the rows an installation already had and 033 the review of the whole catalogue, both only where nobody had changed them.

## Achievements page

**Logros** (menu → Explorar, `#/achievements`) lists every achievement, with its picture, a description (the text it announces with the player and the game made generic) and who of the group has unlocked it (including players who no longer play), how many times (once per season) and when last. The ones you have not unlocked are shown **dimmed with their name only, not the description nor the picture** (a placeholder trophy stands in; the API sends neither, nor the key, because the picture and the key would give away what it is about; they come once you have unlocked it in any season), so you have to work out what they are about, unless they are secret: those appear as "Logro oculto" (see below), with a count at the top. A hidden one says only **how many** have it, never who (`GET /group/achievements` sends no `players` for it); once you have unlocked it you see the names like in any other. **A secret season achievement is only revealed in the season it was earned in**: in any other season of the **Logros** page it is a hidden one again, even for whoever earned it (a secret lifetime one belongs to no season, so it stays revealed). The same rule applies wherever achievements of other players show up: the public player page of another player does not list their secret ones, not even to a player who has them too (it is the only place a secret one is named, on your own page), it only adds "+N logros ocultos" (`hidden_achievements`, no title, date or aura), while the activity feed says it for every secret one to everybody, even whoever has it, and names the player but not the achievement ("<name> desbloqueó un logro oculto", with their photo). The admin panel always shows everything. `GET /group/achievements`, derived from the catalog and the unlocked achievements of every player; nothing is stored. The page has **two blocks**: **De temporada** (earned once a season, counting only what was played in it) and **Lifetime** (key ending in `_LIFETIME`: they count the whole history and are earned once), each with its own "Tienes X de Y" and a header that folds it (open by default; it stays as left while you change season). The season block has **a pill per season** (from 2023 to the running one, the running one by default, like the profile's): each shows only the achievements that existed and were active that season, who of the group earned them **in that season** (so no "×2"), whether you did, and, for the running season only, your progress; `GET /group/achievements?season=<year>`, a future season is a 400. What you have earned in another season does not count as earned in this one, but it does tell you what the achievement is (its description shows), because you have unlocked it once; a secret one is the exception: it is only revealed in the season you earned it in. Before the season pills there is a **Resumen** pill (`GET /group/achievements?summary=true`) that puts every season together: each season achievement once, with who of the group earned it in any season (with the repeats, "×2"), and, for the ones you earned, in full (secret or not) and with the seasons you did ("Conseguido en las temporadas 2024, 2025", the `seasons` field); the ones you lack are dimmed or hidden as in the running season, and there are no progress bars. It is the one view that reveals a secret one outside its season. The lifetime block does not depend on the pill; an empty block is not shown, and a hidden secret one goes in the block it belongs to (the API sends only that, `lifetime`). **Progress bars:** an achievement that adds something up and that you do not have yet shows a bar and "35 / 100" (no unit on purpose: a locked achievement does not say what it counts): total hours, days played, games played, games completed, hours in a single game (season ones count the running season, so one earned in a past season shows how far this season is; lifetime ones count the whole history from the season they start in) and the **current** streak. The ones about a moment (hours in a day, a session, early riser...) and the secret ones have no bar. `progress` of `GET /group/achievements` comes from the same queries and thresholds the checks use (`crud/achievement_progress.py`), so a bar and the unlock agree; nothing is stored.

## Games page

**Juegos** (menu → Explorar, `#/games`) lists every game of the database as cards (cover, name, genres, "En tu biblioteca", "Jugándose", how many players have it, the group's hours and the average rating), each one leading to the game's page. `GET /games/catalog` does the work on the server, derived and nothing stored: search by name; order by latest activity (default, the games nobody has touched last), most played, best rated, most players, release date or name; filters by genre and by your library (all, the ones you have, the ones you do not), and toggles for what is being played right now, games with players, completed by you and rated by you; 24 at a time with **Mostrar más**. **Añadir juego** opens the RAWG search of the timer picker and, once chosen, goes to the new game's page.

## Wishlist and upcoming releases

**Deseados** (menu → Tú, `#/wishlist`) is the list of games you want to play, among them the ones that are not out yet, so there is one place for both and no extra screen. It has two halves: **Próximos lanzamientos** (games without a release date, or with a future one: the nearest first, with a countdown and the date; the ones without a date, shown as "Sin fecha confirmada", last) and **Quiero jugar** (already released, the latest wish first). Each card says which other players want the same game ("Lo quieren Bea y Cai") and has a × to take it off. `GET /group/wishlist`.

- **Adding**: **Añadir juego** uses the same RAWG search as the Juegos page (a game that is not in the database yet is created from RAWG after a confirmation), and the game's page has **Añadir a mi lista / Quitar de mi lista** when the game is not in your library. `PUT`/`DELETE /users/{username}/wishlist/{game_id}`, yours or an admin's; asking again is harmless, a game that is not in the database is a 404 and one that is already in your library a 409. Only games RAWG knows can be added (an announced game usually is, with a future date or none); a game RAWG does not have is not supported for now. The Juegos page marks the ones in your list ("En tu lista").
- **Only the wish is stored** (`users_wishlist`: user, game, when). Whether a game is upcoming, whether it is in your library and who else wants it are derived. **A wish stays until you remove it**, even once you play the game (an early access, say): the card then carries an "Ya en tu biblioteca" tag, and the calendar, the notices (private and group) and the "who wants it" lists keep counting it. Only active players count, never the emergency account.
- **Release dates slip**: every day at 09:00 the scheduler (`daily_wishlist`) asks RAWG again for the date of each game somebody still waits for that is not out (or comes out today; one call per game, at most 50 per run) and writes a date only when RAWG gives one, never blanking it. Then it tells each player, by Telegram and push like the other private notices, which of the games they wished come out **today** and who else is waiting for them, in one message for all of them. Each player chooses the channels in **Perfil → Ajustes → Notificaciones** ("Sale un juego deseado": a Telegram and a push checkbox, both on by default; with both off the notice is not sent, and a channel the player cannot be reached by does not count). It is independent of the group's notice below. Nothing is remembered between runs: a game comes out on one day only, and a day the API was down is not made up for (the 3 hours of grace of the daily jobs apply).
- **To the group, one way at a time** (admin panel → Envíos → Juegos deseados que salen, `wishlist.group_notice`): **the day before** (the default), **the same day**, **once a week** or **none**. It is a single choice, so two never go out. They are group notices (Telegram and push), take the same grace window and have no catch-up. **They do not look at the library**: a game is told to the group, with everyone who wished it, even if they have played it already, so the rest of the players hear of the release (only the private notice above leaves out who already has the game).
- **The day before, to the group** (`eve`): every day at the notice time (`wishlist.time`, 12:30 by default, after the 09:00 refresh, so a date that slipped is already corrected; `wishlist_eve`) one message goes to the group, like the other group notices (Telegram and push). It opens with a header that counts the games ("Mañana salen 4 juegos", or "sale 1 juego"; on a push it is the title) and has one line per game that comes out **tomorrow**: the game and, in brackets, the names of who waits for it ("Ana", "Ana y Bea"). Nothing is sent if there is none. It can be rewritten by the AI (use `wishlist_release`, "Sale un juego deseado": switch and prompt in the admin panel like the others; without the AI it is the plain text).
- **The same day, to the group** (`day`): the same message, at the same time, for the games that come out **today** (header "Hoy salen 4 juegos"; `wishlist_day`; AI use `wishlist_day`, "Sale hoy un juego deseado"). It is independent of each player's private notice of the release day.
- **Once a week, to the group** (`weekly`): every Sunday at the same notice time (`wishlist_week`) one message with a header that counts the games ("Esta semana salen 4 juegos", or "sale 1 juego"; on a push it is the title) and one line per game that comes out in the **7 days that follow** (from tomorrow), by date: the weekday and day, the game and, in brackets, the names of who waits for it ("Ana", "Ana y Bea"). Nothing is sent if there is none. It can be rewritten by the AI (use `wishlist_week`, "Salen juegos deseados esta semana").

## Release calendar

**Calendario** (menu → Explorar, `#/calendar`) lays out on a month grid (Monday first) **every game of the catalogue that has a release date**, whether anybody wants it or not and whether it is out already or not: each sits on the day it came or comes out. A day with one release shows the game and **is a link to its page** (hovering shows who wants it); a day with several shows how many and highlights its games in the **Juegos del mes** panel. That panel sits beside the grid on a wide screen and below it on a phone, and lists every release of the month by date, each game a link with everybody who wants it ("Lo quieren tú y Bea"; nothing when nobody does); the first day with several games is selected on opening. The arrows move between any months, past ones included (the page opens on the running one, and a **Hoy** button beside the month name brings you back to it from any other), and the games with no confirmed date are listed apart under **Sin fecha confirmada**, but only the ones somebody wants (most of the catalogue has no date, and listing it all would bury the rest). `GET /group/releases?month=YYYY-MM` (default: the running month), readable by any logged-in user on purpose, like the players pages; only active players' wishes count as "who wants it", never the emergency account's. Derived from the catalogue's release dates (the daily refresh keeps up to date those of the wished games) and the wishes ([Wishlist](#wishlist-and-upcoming-releases)); nothing is stored. A phone calendar feed (`.ics`) is not built.

## Challenges

**Retos** (menu → Tú, `#/challenges`) are goals with a start and an end, unlike the achievements: they are **launched** by someone, about something **specific** and **shared**. There are three kinds, and where each is made says which is which (`challenges.scope`: `group`, `user` or `duel`): the **group's** challenges are the app's, launched and deleted by an admin **only from the admin panel** (**Jugadores → Retos → Lanzar juego del mes**, `POST /manage/challenges`, which the audit log records), and the **personal** ones are launched by a player for themselves **only from the Retos page** (`POST /challenges`, which refuses a group template for everybody, admins included). Plain accumulation (hours, days, games, completions) stays an achievement. Each kind of challenge is a **template written in code** (`utils/challenges.py`, `TEMPLATES`); whoever launches one only fills in its options, so a new challenge needs no deployment. **Only the definition is stored** (`challenges`, and `challenge_optouts` for who left): progress and whether it is met are derived from the sessions and the library when asked, so they follow any correction to them (AGENTS.md rule 2).

- **Juego del mes** (`game_of_month`, a **group** challenge launched from the admin panel): a game, a month, a minimum of hours **per player** and a minimum **in total**. Each participant's hours are the finished sessions of that game that **began** within the month. The page shows a bar per player (green once their minimum is reached) and one for the total.
- **Temático** (`themed`, a **group** challenge launched from the admin panel with **Lanzar reto temático**): a tag of the games (RAWG's: Horror, Singleplayer...; the form offers those that exist in the database with how many games have each, `GET /manage/challenges/tags`), a month and what each player has to do: **play** a number of hours, or **complete at least one game**. **Every game that has the tag counts** (the tag is matched as a whole word of the game's list of tags, not as a piece of text). Hours are the finished sessions that began within the month and a completion is a `completed_date` within it. The **group total is optional**: hours between everybody (play) or games completed between everybody (complete); when it is set it is drawn as a bar and, when reached, the group is told once (the same notice as the game of the month), and when it is not there is nothing to reach, so only the launch is announced. Tags come from RAWG, so only games the sync filled in have them.
- **Probar un género** (`new_genre`, a **personal** challenge, launched from **Retos → Nuevo reto**): the player picks a genre that exists in the database and has games (the list says how many and which ones are new to them, `GET /challenges/genres`), the goal and how long it lasts. The goal is to **play** a number of hours (2 by default, the player's choice) or to **complete** one game; the duration is one week, one month (the default) or three months, and the deadline is worked out from it: the period starts the day it is launched and counts that day (7, 30 or 90 days), and both dates are stored with the definition. **Only games of that genre that the player did not have in their library before it began count** (a game already in the library from an earlier date does not): hours are the finished sessions that began within the period, a completion is a `completed_date` within it. Every player sees the others' personal challenges (they are public), but only the owner can delete theirs, and nobody is told about them: no launch or total notice.
- **Bajar la deuda** (`debt_reduction`, a **personal** challenge from **Retos → Nuevo reto**): a goal about the [debt](#average-times-and-the-debt-ranking) the player has when they launch it, and only about the games they **already had open** then (a session of 10 minutes or more before it, not completed, not abandoned, with an average time; the debt is worked out from what happened before that day, `debt.games_in_debt_at`, so it does not drift when the HLTB times are synced again). Two modes, with a free number: **a percentage** (1 to 100) of what was left to play, or **a number of games** (1 up to how many are open) to close. Playing a game that was open pays what was played, up to what it had left; **completing it pays all it had left**; **abandoning it pays nothing**; a game started afterwards neither pays nor costs. The percentage is the share paid over the debt at the start; "games" counts the completions (a `completed_date` within the period) of the open games, including one already past its average time. The form says what a percentage means **before it is accepted** ("El 25 % de tu deuda son unas 10 h"; `GET /challenges/debt` has the debt it would start from) and does not launch one when there is nothing open (a percentage also needs some time left). The period is chosen like the genre's (a week, a month or three months, starting today).
- **Four more personal templates**, all derived from the sessions and the lists, with the period chosen like the genre's (a week, a month or three months from today) and the progress drawn as a count with a `unit` (`days`, `sessions`, `genres` or, without it, `games`) that the front names:
    - **Racha** (`streak`): `consecutive` (the longest run of days in a row within the period) or `days` (how many different days), from 2 up to the length of the period. A played day is the one of the streaks and the achievements: a finished session of 10 minutes or more, counted in the day it began and the one it ended (`time_entries.played_days_by_user`).
    - **Sesiones largas** (`long_sessions`): how many finished sessions (1 to 100), of any game, last at least so many minutes (15 to 600) and began within the period; manual sessions count like the others.
    - **Variar de género** (`variety`): how many different genres (2 to 10, and no more than the database has) get at least so many hours (half an hour or more, 1 by default) within the period. The time of a game counts in **each** of its genres.
    - **Cumplir deseados** (`wishlist`): `start` or `complete` a number of games (1 up to the wishes the player has pending) among the ones they were **already waiting to play the day it was launched**: on their wishlist by then (added that day or before) and not in their library with an earlier `started_date` (`wishes_at`). Starting is the `started_date` of the entry within the period, completing its `completed_date`. A wish removed from the list afterwards stops counting, like any figure that is derived from what is there.
- **Duelo de horas** and **Duelo en un juego** (`duel_hours`, `duel_game`, scope `duel`, from **Retos → Nuevo reto**): a player challenges **another active player** (`params.opponent_id`; the challenger is `owner_user_id`) to play more hours, of any game or of one game of the catalogue, in a week, a month or three months starting today. Hours are the finished sessions that began within the period. Whoever plays more **wins** (`done`, with `position` 1 and `winner`); a tie with something played is won by both, and nobody wins when nobody played. The bar of each is against the leader's hours. **It starts as soon as it is launched** (no acceptance step, so no table was added): the challenged player may **decline** it during the first 48 hours (`DECLINE_HOURS`, from `challenges.created_at`) with `PUT /challenges/{id}/participation?joined=false`, which writes the same `challenge_optouts` row a player leaving a group challenge does. **A decline is final** (a duel needs no acceptance, so `joined=true` is refused with 409), which also keeps the challenger from being told over and over; after the 48 hours the duel stands (so nobody dodges a duel they are losing). A declined duel shows "Rechazado", leaves the history, the Home card and the achievements of both, and a duel **never counts for the achievements of the challenges met** (it is easy to win one against nobody; how a duel should count is left to think over), and only the challenger can delete it. An equal duel (same players, game and period) is refused, the other way round is another. Duels are public, like the personal challenges, and nobody is told about them. An acceptance step with an expiry is a possible later improvement that would need a migration.
- **Versus mode for a group challenge**: the admin can launch a game of the month or a themed challenge as a **contest** too (`params.versus`, the "Además es una competición" switch). The challenge keeps its goals; besides, each part gets a `position` (1 is the best, a tie shares it) and `winner` (first with something done), worked out from what each has reached (`rank_players`, pure), and the page shows medals and "· 🥈" in the player's own line. It can be read while it runs and is final when it ends; nothing is announced for it but the launch notice says who plays the most wins. A player's history says "Empate" for a shared first place.
- **Who takes part**: in a group challenge every active player does, and each one can **leave** (and come back) while it is not over (`PUT /challenges/{id}/participation?joined=`); a player who left is not counted in the bars or the total, nor in their history. A group challenge can also be **voluntary** (`challenges.participation = 'opt_in'`, chosen by the admin when launching it: "Quién participa"): then **nobody** takes part until they join (an "Apuntarme" button, the same `PUT` with `joined=true`), and only who joined counts in the bars, the total, the history and the achievements; the launch notice adds "Es voluntario: apúntate en Retos". Both modes use the same table, whose row is *a choice against what the challenge assumes*: in an `auto` challenge a row means the player left it (or declined a duel) and in an `opt_in` one it means they joined, so nothing was added for this (an inactive player is never counted either way). A voluntary challenge has another fingerprint than the same one for everybody, so both can exist. A personal challenge has its owner as the only participant, who cannot leave it; visibility is `public` for everything (the column exists so a challenge can be private later).
- **Proposals of the players** (`challenge_proposals`, migration 042): a player can **propose** a group challenge, a game of the month or a themed one (**Retos → Proponer al grupo**, `POST /challenges/proposals`; `GET /challenges/tags` lists the tags they can choose from). A proposal is checked **like a launch** (`crud/challenge_proposals.py`: the same `build` of the template, so an admin is never asked to approve what cannot be launched), keeps only the options a group template knows (`GROUP_OPTIONS`) and is refused with 409 if the player already has **3 waiting** (`MAX_PENDING`), if an equal challenge exists or if an equal proposal is waiting (both by the fingerprint of the challenge it would be). The player sees their proposals, with the answer, under **Tus propuestas**, and can **withdraw** (delete) one that is still waiting. In the admin panel (**Jugadores → Propuestas**, `/manage/challenge-proposals`) an admin **approves** it, which launches it as a challenge of the group *created by that admin* (choosing who takes part and whether to tell the group; `POST .../{id}/approve`), or **rejects** it with an optional note the proposer reads (`POST .../{id}/reject`). It is decided once; approving fails with the reason if it cannot be launched any more (the month has passed, the game was deleted: the admin rejects it). The panel's home lists the waiting ones under "Requiere atención" (`pending_challenge_proposals`). Deleting the launched challenge leaves the proposal (`challenge_id` goes to NULL) and deleting the proposal leaves the challenge. The audit log records every decision. Nobody is notified outside the app yet.
- **Recurring challenges** (`challenge_schedules`, migration 043; **Jugadores → Recurrentes**, `/manage/challenge-schedules`): an admin defines a group challenge that **launches itself every month**: a **themed** one with fixed options or a **game of the month** whose game **rotates along a list** (up to 24 games, in order, starting over when it ends). Only the definition is stored: the game of a month is derived from the list and `first_month` (`rotating_game`: the months since it began, modulo the length of the list), so changing the list changes the game of the coming months. It starts **next month** unless "Lanzar ya el de este mes" is ticked (the running month is then launched at once). A daily job, `challenge_schedules` (06:00, in `utils/scheduler.py`), launches the running month of each active schedule that has not done it (`launch_due`): `last_month` is what keeps a month from being launched twice, a day the API was down is made up for the next one, and the challenge is created by the admin who defined it (or with no creator if that account is gone). **If it cannot launch** (the game was deleted, the tag disappeared) or an equal one was launched by hand, the month is marked done anyway and the reason is kept in `last_status`, shown in the panel, instead of trying again every day. A schedule is checked when it is defined (the challenge of the running month is built as a trial), can be paused, can be voluntary and **does not tell the group unless it says so** (off by default). Deleting it leaves what it launched.
- **A personal challenge and a duel count from the moment they are launched**, not from the start of that day (`utils/challenges.starts_at`, from `challenges.created_at`; a group challenge counts its whole first day): sessions that began earlier that day are not part of it. A game started or completed has only a date, so on the launch day it counts only if the player has a session of that game from the launch on (`played_after_launch`); the same moment fixes the wishes pending (`wishes_at`) and the debt (`games_in_debt_at(since=)`) a challenge starts from.
- **The list is limited to what the page shows**: `GET /challenges` works out the progress of every challenge it returns, which grows with every one ever launched, so the page asks `?finished_per_block=5` (the running ones and the latest five finished of each block: the group's, yours, your duels, the others') and its **Ver todos los terminados** button asks for all of them; the Home asks `?status=active`.
- **No duplicates**: each challenge has a fingerprint (template, options, game, period and owner) that is unique in the database; launching an equal one answers 409 "Ya existe un reto igual".
- **Notices to the group** (never per player): when a group challenge is **launched** (a switch in the launch form, on by default) and **once** when the group's **total is reached** (checked after each stopped timer or session change that is not silent, recorded in `total_notified_at`; an admin's changes do not announce), and, the day after it ends, **how it ended** (one message: how many met their part, whether the total was reached and who won if it was a contest; `challenges.result_notice`). Telegram and push, like the other group notices. **A personal challenge or a duel is never told to the group**, without exceptions.
- **Private notices** (`utils/challenge_notices.py`, text built by pure functions): what concerns a player goes **only to them**, through the channels they left on for it in **Perfil → Notificaciones** (`user_settings`, migration 044; both channels off means no notice at all, not even in the inbox):
    - **Tus retos** (`challenge_notices_telegram/_push`, **on** by default): the challenged player is told of a **duel** when it is launched (and for how long they can decline it); the challenger is told when it is **declined** (once: asking twice tells nobody twice, and taking the decline back tells nobody); the proposer is told how a **proposal** was answered (with the note); and, the day after, **how their challenges ended**, one message per player listing all of them (a duel says who won and by how much, a group one the place in a contest). A declined duel says nothing to anybody. They go to the inbox too.
    - **Recordatorio de retos** (`challenge_reminders_*`, **off** by default, each player turns it on): when a challenge has **exactly two days left** (`REMINDER_DAYS`) and the player has not met their part, one message per day with all of them and what is left; in a duel, only whoever is behind. A reminder only matters at the moment, so it is not kept in the inbox.
    - **The admins** find a **new proposal** in the inbox of the app only (no Telegram, no push; the panel's home lists it too).
- **No "already told" is stored.** Each notice is triggered by an exact condition (it ended yesterday, it has exactly two days left, the request that made the event) and the two daily jobs run once per slot (`job_runs`), so there is nothing to remember and nothing to repeat. The jobs are `challenge_results` (09:30 by default) and `challenge_reminders` (10:00), each with its hour in **Notificaciones → Envíos → Retos**, where the admin also has the switches: private notices, the result to the group and whether the reminders exist at all (`challenges.private_notices`, `challenges.result_notice`, `challenges.reminders`). All of them need the general notifications switch. A run missed because the API was down for more than the grace window (3 hours) is not made up for: its day is simply not told.
- **How a player stands** (in the app only, nothing is sent): the Retos page shows, on each challenge the viewer takes part in, a line worked out in the front from the progress it already has (`standing` in `front/js/lib/challenges.js`; nothing is stored): *done* (their part is reached), *urgent* (two days or fewer left and not reached; it says what is left), *behind* (past 30 % of the period and trailing the share of time gone by by more than 20 points), *ok*, or only *pending* for a goal of one game, where a pace means nothing. A finished one says whether it was met. The top of the page counts the running ones (`digest`), and the Home has a **Mis retos** card with them, the ones that need attention first (`GET /challenges?status=active`, which keeps the running ones so the Home does not work out the progress of every challenge there ever was). Whoever does not take part in a challenge gets no line for it.
- **History**: a player's finished challenges, with how they did, are in **Perfil → Resumen → Retos** and on their public page (`GET /challenges/player/{id}`, readable by any logged-in user on purpose since the challenges are public). The admin panel (**Jugadores → Retos**, `GET /manage/challenges`) lists all of them, personal ones included, launches the group's and can delete any.
- Only an admin launches or deletes a group challenge, from the panel (`POST` and `DELETE /manage/challenges`, behind the admin router); the Retos page shows them and lets everybody leave or rejoin, nothing more. The API enforces it.

The page shows three blocks: the group's challenges, yours and the other players' (running ones first, only the latest finished ones). Paying down the debt is a template parked in [#120](https://github.com/la-viciacion/la-viciacion/issues/120).

## Playing now

The navbar shows who else is playing right now: a chip with up to three avatars with a green aura (and "+N" for more), only when somebody is. Pressing it opens a bottom sheet on a phone (a normal window on a wide screen) with each player, the game, the platform and how long ago they started. Your own avatar gets the aura while your timer runs. When two or more players have a running timer on the same game (whatever the platform), the sheet shows them in one card, "Bea, Cai y tú estáis jugando a Hades" (you appear only when you are one of them); it only says they play the same game, not that they play together. Nothing is stored: it is the list of running timers of the active players (`GET /timers/now-playing`, never the emergency account), refreshed every 45 seconds while the app is visible, when it returns to the foreground and on every screen change. A timer running for more than **6 hours** is shown dimmed, after the others and with "¿Un timer olvidado?", and does not make the chip appear. Every player can stop appearing to the others with `user_settings.show_playing` (on by default); the profile does not offer it for now (`SHOW_PLAYING_OPTION` in `front/js/pages/profile/index.js`, off), but the setting still works through the API. They still see themselves. The photos come from `GET /users/photo/{id}`, readable by any logged-in user on purpose (only active players, only the image).

The installed app offers shortcuts on a long press of its icon (`shortcuts` in `front/manifest.json`): **Nuevo timer** (`#/new`, opens the game picker unless a timer is already running), **Jugando ahora** (`#/playing`, opens the sheet) and **Mi perfil**.

## Activity page

The **Actividad** page (menu → Principal, `#/activity`) lists what everybody has done, newest first and by day (Hoy, Ayer, then the date), 30 at a time with **Mostrar más** (`GET /activity?limit=&offset=`): each session played (one line per session, with its duration), a game started for the first time, a game completed (with its rating, if any), a rating given and an achievement unlocked (with its game, if it has one; a secret one always comes as a hidden event, without title, game or player, for everybody). Within a day they follow the clock: a session counts when it ended and a rating when it was given; a start, a completion and an achievement only have a day, so they are placed against that player's sessions (a start right before the first session of the game, a completion right after the last one of the game, an achievement right after the last one of the day; with no sessions that day, a start is the first moment of the day and the others the last). Ties go in the order completed, achievement, rated, started, played. Each line shows the player's photo and links to the game page. Every player, active or not (never the emergency account); running timers are not events until they stop. Derived from the sessions, library, ratings and achievements; nothing is stored, so changing a rating moves it to its new date.

## Group library

**Biblioteca del grupo** (menu → Explorar, `#/library`, `GET /group/library`, `crud/group_library.py`; readable by any logged-in user, like the game pages it is made of) looks at every library at once. Derived when asked, nothing stored; every player counts, active or not (never the emergency account). The lists are built by pure functions from a handful of facts (owners, hours, ratings, who gave a game up, genres, platforms) and each is cut to ten items:

**Kept for two minutes.** The group's library and its cost per hour (`GET /group/library`, `GET /group/value`) are the same for every viewer and cost a scan of every library, so each worker keeps the last answer for 120 seconds (`utils/ttl_cache.py`; nothing to invalidate, a change shows up within two minutes, and a restart forgets it). Answers that depend on the viewer or must show a change at once (the home page, the player's own library, rankings of the running season) are not cached.

- **Joyas ocultas**: games with **at most two players** and a **mean rating of 80 or more** (at least one rating), the best rated first and, on a tie, the fewest owners.
- **El cementerio**: games somebody **gave up and has not gone back to**: the abandoned mark of an entry with no session after it, by the rule of `users.is_abandoned`; a game completed that season on any platform never counts. The most abandoned first, then the most played.
- **Rarezas**: games that **exactly one player** has (the owner is named), the most played first, with the total.
- **Sin tocar**: games somebody has and **nobody has ever played**, the most owned first, with the total.
- **Por género** and **Por plataforma**: how many games of the libraries have each genre (a game counts in each of its genres, with the hours put into them) and each platform (with its players), ten at most, the most games first. Only platforms that entries name are listed.

The header has the distinct games, the players who have any and the hours played in them. Under it a row of **pills** (one per section, with how many items it has) reaches every section at once, unfolding it if it was folded and scrolling to it, and each section **folds** on its own with the button of its header; what the viewer folded is remembered in that browser (`localStorage`, only a convenience: without it every section starts open).

## Game page

Pressing a game's name (the history's unfolded rows, the profile's games list, most played and recommendations, the playing-now sheet) opens its page, `#/game/<id>` (`GET /games/{id}/overview`, any logged-in user): cover, genres, RAWG's tags (a second row, without the ones that repeat a genre; an admin can edit them by hand in **Juegos → Editar**, like the rest of the game's data), developer, release date and the average time to complete; the group's figures (players, hours, how many completed it, average rating and how many ratings); your own rating, which you can set or change there; and every active player who has it in their library (any season) with their hours, sessions, seasons, completions and rating, the most played first. A player gets the green aura and "Jugando ahora" while their timer runs (unless it is stale or they hide it, as in the chip). Derived from the library, sessions and ratings; nothing is stored.

**Saga** (`GET /games/{id}/series`, `crud/game_series.py` and `utils/rawg_series.py`): a card after who plays the game (below it on a phone; on a wide screen, 1000 px and up, in a **second column beside it**, always open, and only when the game has a saga: without one the list keeps the whole width; `.gm-lower` / `has-saga`) lists the games of the game's **RAWG series** (`/games/{rawg_id}/game-series`) together with the game itself, **from the most recent to the oldest** (the undated last; the API sends them oldest first, which is what the **Siguiente** mark is worked out from, and the front reverses them), each with the viewer's standing (*Completado*, *En tu biblioteca* with their time, *No lo tienes*, or *No está en la biblioteca del grupo* when the catalogue has no game with that `rawg_id`), how many players have it and a **Siguiente** mark on the first game released after this one that the viewer has not completed; a game of the catalogue links to its page, any other to RAWG. It is a request of its own, made **after the page is drawn**, because it reaches RAWG: the answer is **kept in memory for 24 hours** per worker (requests that arrive together for the same game share one call to RAWG) (at most 500 games, the oldest answer out first; nothing in the database) and a failure for 5 minutes, so opening a page again and again does not spend RAWG's quota. Without a RAWG key, with a game that has no `rawg_id`, with no series or when RAWG fails the card is simply not there (`available: false`). The catalogue's name and cover win over RAWG's. The card **folds** (with how many games the saga has beside its title) and the choice is remembered in the browser.

**Outside data** (`GET /games/{id}/extras`, `utils/game_extras.py`): what Steam and RAWG say about the game, asked when the page opens and kept in memory for a day like the saga (`utils/outside_cache.py`, shared with it: nothing is stored; a failure is remembered for 5 minutes, and so is an answer that lacks what one of the two services did not give in time; both sources are optional: Steam needs the game's Steam app id (its `steam_id`, or, when it has none, the one RAWG's stores link to, found with one more call), RAWG its `rawg_id` and the key, and when neither answers `available` is false and the page shows nothing). Steam: `appdetails` in Spanish (short description, trailer, screenshots, Metacritic). RAWG: the game (Metacritic, age rating, publishers, platforms and its description) and, only when Steam had none, its `movies` and `screenshots`. Metacritic is RAWG's first, then Steam's. **Prices are left out on purpose** (they depend on the store, and a game is played on several platforms), and so is anything that would copy RAWG's page. Media links are kept only if they are https and from `steamstatic.com`, `akamaihd.net` or `rawg.io` (`media_url`). The page (`ui/game-extras.js`, loaded apart so the page does not wait for it) puts the description right **under the name** (Steam's, in Spanish; without it RAWG's, in English, marked **En inglés**; clamped to four lines on a phone and six on a wide screen until tapped), then the **publisher** (a line, only when it is not the developer too) and the **platforms** the game came out on (small pills with RAWG's names, at most 10), the facts as two badges on one row with the **Ver en RAWG** button (Metacritic's number in a green, yellow or red square by its own bands, 75 and 50; the ESRB rating as a boxed letter with its name) and a **Multimedia** card with the trailer (a poster that becomes a `<video>` only when pressed, so no video is downloaded by opening the page) and the screenshots as a **carousel** (swipe, or arrows with a mouse). On a wide screen (1000 px and up) the card dissolves into the header's grid: the trailer on the **right** of the header, the carousel below it across the whole width, all open; on a phone it is one block below the header, open and foldable (the choice is not remembered). Every foldable section of the app (Logros, Biblioteca del grupo, the saga, Multimedia) shares one toggle in `profile.css` (`.ach-chevron`): a labelled pill ("Ocultar" with an arrow up when open, "Mostrar" with an arrow down when folded) so it reads as a control on a phone. With no trailer and no screenshots there is no card (the description still shows); with nothing to say there is nothing. The game's RAWG tags are cut to the first 6 (RAWG sends dozens, the most popular first) with a **+N** button for the rest.

**Pace** (`pace` of `GET /games/{id}/overview`, only for a viewer who has played the game; `game_overview.pace`, pure): a card under the figures compares **your total time on the game** with the **mean time of the other players who completed it** (their total time on it, any season, as a proxy for the time to complete) and with the **average time to complete** (HowLongToBeat's). If you completed it it says how much faster or slower you were ("Eres un 25 % más rápido que el resto del grupo…"); if not, what share of that time you have put in so far. Each comparison is left out when there is nobody to compare with or no average time.

## Profile figures and recommendations

The profile has the layout of the admin panel: a side menu (a collapsible bar on a phone) with two sections, **Resumen** (the default) and **Ajustes**, under a header with the photo and the name. Resumen shows the figures of the running season, with a pill per season the user has played and a **Total** pill (`GET /users/{username}/profile?season=2025|all`): stats, most played games, achievements and the list of games below them (`GET /users/{username}/library?season=2025`, every season for **Total**) follow the pill; the running streak is only shown for the running season and the total. Nothing is stored, each season is computed when asked.

**Mis juegos** (the full list) tells where each pending game stands and what is worth going back to. Nothing is stored: it is worked out in the front (`front/js/lib/library-filter.js`) from the library items (`GET /users/{username}/library`, which now carries `avg_time`, the average time to complete of the game, seconds or `null`). The **state** of an entry is *Completado*, *Abandonado*, *Sin completar* (pending in a closed season), *Pendiente* (never played), *Pausado* (the last session is more than **30 days** old) or *En curso*, and the *Estado* filter has all of them. **¿Qué juego sigo?** (a card above the list, folded away on request, absent when there is nothing to suggest) sorts the games whose entry of the running season is pending, once each, into: **Casi terminados** (from 70 % of the average time up to 150 %, the nearest to the end first; past that the average says nothing), **Olvidados** (played, not touched for **60 days**, the one with the most time put in first) and **Cortos** (4 hours or less left by the average, a game never played included, the shortest first). A game goes in the first list that fits it. The time of a game counts only the runs not completed yet, so a game completed in an earlier season and played again starts over; a game with no average time is only ever *Olvidado*.

The **Recomendados** page (menu → Tú, `#/recommendations`) shows 12 games (the bot, 10) picked at random among all the games other players have and you have never had (in any season). The chance of each one grows with how many players have it, how many completed it, the hours and the sessions the others have put into it, with how much you play its genres, and a little with the ratings (1-100) the others gave it: a well rated game is somewhat more likely and a badly rated one somewhat less, but only as far as enough players rated it, so a game with a single rating, or none, is hardly affected; every visit, or **Otras recomendaciones**, can show different ones, and the ones shown are listed with the most shared first. Nothing is stored: the candidates are computed from the libraries each time. When somebody completes a game, the group notice also recommends a game that shares a genre with it, picked among the same candidates and with the same weights (so a game more players share, completed or play more, that fits what the player plays and is well rated is likelier). The notice only recommends the game, never who has it: the AI is told why it was picked (genre in common, how many players have or completed it, the group's rating when enough players gave one, whether it fits the player's genres) and may argue with that; without the AI it is a plain line with the game's name. It can be switched off (see AI-written notices).

## AI-written notices

**Welcome to the group.** The bot welcomes whoever joins the app's group (a join in any other group gets no answer) and tells them to use `/activate`. The text is the one use of the AI that is not a rewritten notice: the bot asks the API (`POST /manage/welcome-message`, with the name and the @username the person has, or none) and the API asks the AI with the `welcome` prompt (its own switch, editable like the others; `utils/welcome.py`). The answer is used only if it is plain, short (600 characters at most) and still contains `/activate`; the API gives `null` otherwise, when the AI is off or when the provider fails, and the bot then sends its fixed welcome (`bot/src/utils/messages.py`), which also says to set an @username first when the person has none. The bot waits up to 40 s for the API (the provider's own limit is 30 s) and handles the join without blocking its other chats, so a welcome always goes out.

**What the AI costs.** Panel Sistema -> Uso de IA (`GET /manage/ai-usage`) shows what OpenAI billed: the total, per month, per line item and, for a chosen month, per day. It asks OpenAI's Costs API with `OPENAI_ADMIN_KEY` (an admin key, or a restricted one with only `api.usage.read`; never `AI_API_KEY`) and keeps the answer in memory for 10 minutes: nothing is stored, so there is no ledger to drift (rule 2). OpenAI keeps one year of spend and refuses an older start date, so a year is the most the panel can show, and it is the whole organization's bill, not only this app's. There is no remaining-credit endpoint. Google has no spend API: Gemini's cost is not shown.

The AI rewrites some notices of the group (a new game, a completed game, the rankings) in a funnier way; without it they go out as plain text. It is managed from the admin panel (**Notificaciones → IA**, cards **Inteligencia artificial** and **Avisos que usan la IA**): an on/off switch and **Probar la IA**, which asks the configuration in use for one sentence and shows the answer or the reason it failed. The provider (**Google Gemini** or **OpenAI**), the key and the models in use are shown, read only, in **Sistema → Servicios**, where everything the server's `.env` configures is together (the AI, Telegram, the push contact and keys, and the mail).

`AI_PROVIDER`, `AI_API_KEY` and `AI_MODEL` are read from `.env` every time and **never stored**, and **the code has no default provider or model**: they cannot be changed from the panel (which shows them, or says which is missing), and without all three the AI writes nothing and the notices go out as plain text (the model must be one of the provider). Each notice that can use the AI has its own switch and its own editable instructions (prompt) under **Avisos que usan la IA**: a new game, a completed game (and the suggestion of another game it may carry: that suggestion has its own switch, `completed_game.recommend`, on by default and **not an AI one**: switched off, no game is suggested, with or without the AI; switched on, the AI writes it with its own instructions and, when the AI does not write the notice, a fixed line with the game is added), a change in the games ranking and a change in the hours ranking. What the AI knows is only the message of the notice, and what it keeps is what its prompt asks: the notice of a completed game says who, the number of games completed this season, the game, **how long it took the player** and, when it is known, the average time to complete it, and its prompt asks the AI to keep the player's time and the average and to speak of the player in the third person (the notice goes to the group, not to them) (`tests/test_notice_contracts.py` pins, for every notice, what its message carries against what its prompt asks). The default prompts all ask the same of the AI: start with the message itself (its names and figures in the first sentence, the rankings with the original list right after their title) and add at most one short joke, in two sentences or about 250 characters; the recommendation is one last short sentence. The prompts in `api/src/utils/ai_prompts.py` are only the defaults: nothing is copied to the database until an admin edits one, from then on the edited text wins, and **Restaurar las originales** goes back to following the code (so an improved default reaches everybody who never changed it).

**When the AI runs out of quota.** A provider's free tier has limits per minute and per day that nobody publishes as a table (Google sends people to AI Studio), so the only way to learn them is what the provider answers when it refuses a call: an HTTP 429. Every 429 of a provider is recognized (`clients/quota.py`: Google's `RESOURCE_EXHAUSTED` with its `QuotaFailure` and `RetryInfo`, OpenAI's `insufficient_quota` and `retry-after`, and what pydantic-ai wraps) and becomes a `QuotaError` that says which quota ran out (its id, its limit, whether it is per minute, per day or the billing), and how long to wait. It is written to the audit log (`utils/ai_quota.py`): event `ai_quota`, user `sistema`, and in the detail who asked (`chat`, `chat_test`, `ai_test`, `welcome` or `notice:<use>`), provider, model, the quotas, the limit and the wait. The panel lists it as "Se agotó el cupo de la IA por día al pedirlo el chat" (filter **Tipo → Accesos, seguridad e IA**). A quota that has run out refuses every call until it recovers, so the same one is written once every 10 minutes, and the refusals in between are counted in the next row (`repeated`). It is a warning in the log, not an error, so it does not fill Sentry. The notices carry on as plain text, the chat answers 429 "El cupo de la IA se ha agotado (reintenta en N min)", and the test buttons show the quota that ran out.

## Chat assistant

A floating button at the bottom right of every page (a full-screen sheet on a phone, a 380 px panel on a wide screen; it hides on the story) opens a chat that answers questions **only about video games and the group's data**. The button appears only when `GET /chat/status` says the chat can answer: it is switched on (`chat.enabled`) and the AI is configured for it. `POST /chat {message (500 chars), history (up to 10 turns)}` answers `{answer, in_scope}`.

**Settings.** The chat has its own switch and instructions (`chat.enabled`, `chat.prompt`: editable and restorable like the notices', and not depending on the notices' switch, nor the other way round). **The provider and the key are the AI's** (`AI_PROVIDER`, `AI_API_KEY`), and **the model is the optional `CHAT_AI_MODEL`**: without it the chat uses `AI_MODEL`, so a stronger model for the chat is the one thing that may differ. All three are read from the `.env` every time, never stored and never changeable from the panel (`env_only`). In the admin panel it has its own tab, **Sistema → Chat**: the switch, the instructions, a line saying whether the players have the button now and, if not, why (switched off or which variable is missing), and **Probar el chat**, which asks its model for one sentence (`POST /manage/settings/test-chat`, works with the chat off). Switching the chat off stops it at once: a player who already has the page open sees the error on their next question and the button goes when they close the panel; the others lose it on the next load.

- **Questions about the app.** `app_help` answers how the app works (logging in, timers and sessions, completing and rating, seasons, days and streaks, achievements, profile, the group's pages, wishlist, recommendations, challenges, the summary, notifications and Telegram, who sees what, the chat). The guide (`docs/guia-usuario/`) is not shipped in the API's image, so `chat/help.py` holds a short summary of each topic, each naming the guide page it comes from (`source`); a test checks that every source exists, and finds each topic from its own title and keywords. **Whoever changes a page of the user guide should look at its topic there**, or the chat keeps answering what the page used to say. The model is told to answer only from what the tool returns and to say it does not know otherwise.
- **What to ask.** An empty conversation offers three questions picked at random from a list of about forty-five (`SUGGESTIONS` in `front/js/lib/chat.js`), different each time a conversation starts (when the page loads and with **↺**). They are all questions the tools can answer: rankings and activity of the group, one's own figures, the wishlist and the catalog by genre or tag. Some are about the app and the chat itself. Each one must be answerable with one or two calls of the tools: a question that needs a call per player, or that leaves the model to decide what to look at, can run out of the limits below (that is why there is `affinity_with_players` and a `kind` filter in `recent_activity`). A new tool should come with questions here.
- **How an answer is drawn.** The model writes a little Markdown and the chat draws it: `*italic*`, `**bold**`, `` `code` ``, headings (as a bold line) and bulleted or numbered lists. Nothing else is interpreted (no links, tables or HTML), and none of it becomes markup: the front builds the elements from the parsed parts (`parseAnswer` in `front/js/lib/chat.js`), so what the model writes cannot add a tag, an attribute or a link. A stray asterisk stays text.
- **Nothing is stored.** The conversation lives in the browser's memory (it survives changing page, not a reload or logging out) and the front sends the last turns with each question; the API keeps no history, so there is no table and no migration.
- **The agent** (`api/src/chat/`, [pydantic-ai](https://ai.pydantic.dev)) is built per request (`chat/model.py`: OpenAI or Google, as the notices). Its answer is structured (`in_scope`, `answer`): a question the model marks out of scope gets a fixed reply, whatever it wrote.
- **What it can look up** (`chat/tools.py`, all read-only wrappers over the CRUD the pages use, at most 10 items each, hours already in hours): `search_games` (name, genre or tag; the catalog's genres and tags are RAWG's, in English, so the common Spanish words are translated and an empty search tells the model to stop looking), `game_info` (who has it, hours, completions, ratings), `players`, `player_profile` (season or all), `ranking` (hours, days played, streaks, completed and played games, achievements, completion ratio), `most_played_games`, `recent_activity` (optionally one kind of event), `affinity_with_players` (the user's affinity with everybody in one call), `my_wishlist`, `achievements` (the catalog as the Logros page shows it: a description only for what the user has, hidden ones only counted, so the chat never spoils what an achievement is about), `chat_limits` (the limits of the chat and how much of each is left to the user and the group) and `app_help` (below). It sees the group as the asking player does: never another player's library, email, Telegram id or settings, and hidden achievements stay hidden. A tool that gets a name it cannot resolve answers with the options, and the model retries.
- **Speed.** A question is answered from what the tools return, so the model's reasoning is switched off (`thinking=False` in `chat/agent.py`: on Gemini 3 the lowest level, on Gemini 2.5 a zero budget, on an OpenAI model that does not reason nothing is sent); with it on, a plain question such as "how many questions do I have left" took 40 to 48 s. A model that always reasons (Gemini 2.5 Pro, an OpenAI reasoning model) ignores it: for the chat pick a fast model in `CHAT_AI_MODEL`. Every answered question logs how long it took, the model requests and tool calls it made and the tokens ("Chat question answered in 4.2 s: 2 model requests, 1 tool calls…"), to tell a slow model from too many calls.
- **Limits**: 10 model requests, 8 tool calls and 60,000 tokens per question (the tokens of the whole run, a reasoning model's thinking included: a cap on the output alone cut a plain question short), 30 s per call. A question that runs into one gets "divide it", and the limit it hit is written to the log as a warning to tell a big question from a tight limit, and the number of questions asked, which the admin sets in **Sistema → Chat** (`chat.limit_*`, 0 = no limit): per player in the last minute, hour and 24 hours (5, 30 and 100 by default) and for the whole group in the last minute and 24 hours (10 and 300), because the provider's quota is the project's, not each player's, and a limit per player does not stop six players together from using it up. A question over a limit gets `429` with which limit it was ("Has hecho demasiadas preguntas en la última hora" or "El grupo ha hecho demasiadas…"), how long to wait and `Retry-After`. The day is the last 24 hours, not the calendar day. The count is in memory (`UsageLimiter` in `utils/rate_limit.py`, enough for the single API replica): restarting the API sets it to zero, and a question that is refused is not counted, one that fails at the provider is. Changing a limit applies to the next question. When the provider fails the player is told what happened with a joke about being on the free tier (`utils/messages.py`, `CHAT_*`): a timeout (HTTP 408 or 504, or our own 30 s) is a `504`; an overload (503, 529), a server error (the other 5xx) and a refusal of the key or the project (401, 403) are a `502`, each with its own text; anything else is a `502` with the general one. It is never a `503` for the provider: the front reads that as "the chat was switched off" and removes the button. A timeout or an overload is logged as a warning (not an event in Sentry, it is not ours), the rest as an error, always with the error without the key (`clients/failure.py`; the quota keeps its own `429` and rows in the audit log).
