# Features and how they behave

What the app does and the rules behind it, from the point of view of whoever runs it or uses it. The settings that go in `.env` are in [configuration.md](configuration.md); the code behind each rule is in [architecture.md](architecture.md).

## Seasons

A season is a calendar year. It is **never written by the app**: the `season` column of `users_games`, `game_timers` and `users_achievements` is generated by the database from the row's own date (`started_date`, `start_time`, `date`), so it can never disagree with it. To put a library entry or a session in another season, change its date. The running season is the year of today's date on the server (`api/src/utils/seasons.py`); keep `TZ` set so the season changes at local midnight.

The library of the 2023 and 2024 seasons (kept in the `_archived_users_games_*` tables since the yearly tables were retired) is restored into `users_games` by migration 011, so every past session has its library entry. The archive tables are left as they were.

## Notifications and scheduled jobs

Everything Telegram-related is managed from the admin panel (**Notificaciones → Ajustes**), not from `.env`:

- **Settings** live in the `app_settings` table: general notifications switch, admin-alerts switch (independent), weekly summary on/off + weekday + time, and the Telegram bot token, group id and admin chat id. The token is stored encrypted (key derived from `SECRET_KEY`; if you rotate `SECRET_KEY`, enter the token again) and the panel never shows it back; only the bot (logged in as the superadmin) reads it, through `GET /manage/settings/telegram`. `TELEGRAM_TOKEN`, `TELEGRAM_GROUP_ID` and `TELEGRAM_ADMIN_CHAT_ID` in `.env` only **seed** the table the first time the API starts.
- The **bot** reads its token and chats from the API and restarts itself (Docker brings it back) within about a minute when they change.
- **Scheduled jobs** run inside the API process (`api/src/utils/scheduler.py`), so no external cron is needed: weekly summary (private message to each active user with a Telegram id or a push device), (the pinned timer notification is only sent when the timer starts: its periodic refresh is switched off, `TIMER_NOTICE_REFRESH` in the scheduler), hourly forgotten-timer check that reminds once per timer (after 4 hours by default; each user can switch it off, choose whether it reaches them by Telegram and/or push, and choose their own whole number of hours, 1-24, in Profile → Ajustes → Notificaciones; a channel the user cannot be reached by, such as Telegram without a linked account or push without a device, does not count, and with none left no check is made), daily 05:00 check (achievements and lost streaks), daily 09:00 wishlist check (see [Wishlist](#wishlist-and-upcoming-releases)). Each run is recorded in `job_runs`, so a restart never repeats a run, and a job that was due while the API was down still runs when it returns (weekly summary: within 6 hours). Achievements and ranking announcements are event-driven: when a timer stops or an admin asks for it, everything is checked; when a timer starts, only what a running timer can unlock (early riser, nocturnal, teamwork) and the "new game" notice, once per game and season; completing a game also checks the completed-games achievements. Manual sessions never notify. Totals, rankings and streaks are never stored: they are computed from the sessions when requested, so a new season simply starts at zero.
- Each user can set their own Telegram id in their profile and admins can edit it for anyone; it is unique.

## Push notifications (installed PWA)

A second channel next to Telegram, **on by default**, with nothing to set up: the API creates its VAPID keys (one pair for the whole server, shared by all users) on the first start and uses `SMTP_EMAIL` as the contact towards the push services unless **Notificaciones → Avisos en la app (push)** sets another one or turns the feature off. It needs HTTPS. Nobody is subscribed automatically (browsers require a click and a permission per device): the app offers it once after login, and each user chooses for themselves, from their profile (**Avisos en la app**), which of their devices get notifications and whether each also gets the group ones; on iPhone/iPad the app must be added to the home screen first (iOS 16.4+).

- What goes to the Telegram group is also pushed to every device that has group notices on (a per-device switch); private notices (a forgotten timer, the weekly summary) go only to that user's devices.
- **Notificaciones → Redactar aviso** in the admin panel is a composer: title (80 characters) and message (240), with a live preview. Each notice goes through **one channel at a time**, chosen in the composer: the **app** (push: where a tap opens, an optional https image, to your own devices to try it, to one user, to the devices that want group notices or to every subscribed device) or **Telegram** (`POST /manage/telegram/announce`: to your own private chat, to one user's, or to the group; the title in bold, no link or image). Sending to a group or to everybody asks for confirmation. Plain text only; the image shows on Android and desktop, not on iPhone/iPad. These manual notices ignore the general notifications switch, like the test message. The **Avisos en la app** card of **Notificaciones → Ajustes** shows how many devices and users are subscribed.
- **Timer notification**: while you have a timer running, every subscribed device of yours shows a pinned, silent notification with the game and the time played, shown when the timer starts (its periodic refresh is switched off for now, and so is the interval setting in the profile). Tapping it, or its **Parar** button, opens the app, where you stop the timer (no button on iPhone/iPad). When the timer stops, from wherever, the notification turns into "Timer parado · 1h 25min". On iPhone/iPad it is refreshed but not pinned. It follows the general notifications switch and, for now, there is no per-device switch for it.
- Expired devices are removed automatically. Regenerating the keys unsubscribes every device.
- The pushed text is the same message as Telegram's without Markdown, cut to a title and a short body; how long messages and images fit is pending (see [roadmap.md](roadmap.md)).

## Platform catalogue

**Gestión de datos → Plataformas** in the admin panel manages the platform catalogue used by sessions and library entries: add one (its id is made from the name and never changes), rename it (everything that uses it follows), and delete one that nothing uses (a platform that still has sessions or library entries is refused and the message says how many). **Sesiones** and **Biblioteca** next to a platform jump to those rows.

## Revoking achievements

In the admin panel, **Gestión de datos → Concedidos** lists what each player has unlocked (filter by user or game). **Editar** changes the date it was obtained (its year is the season) and **Revocar** removes it without announcing anything. Achievements are re-evaluated on every check (after each stopped timer, the 05:00 job and the admin **Comprobar logros**), so if the player still meets the condition it will be unlocked again: correct the data that triggered it first (e.g. a wrong session).

## Manual sessions

From the home page a user can add a finished session by hand (**+ Sesión manual**: game, platform, start, end) and correct or delete one of their own from **Perfil → Resumen → Juegos → Sesiones** (the sessions of that game and season; **Editar**, only for the current season). In the home list of latest games, pressing a game's row unfolds its latest sessions (**Editar**, **Ver todas**), the check button (gold, green once the game is completed this season) opens a window to mark it as completed (once per game and season, announced to the group after a confirmation) and the play button starts a new timer. The API (`POST /timers/manual`, `PATCH`/`DELETE /timers/{id}`) enforces: the end after the start and not in the future, at most 24 h, **current season only** (closed seasons are frozen; admins can still edit them), and no overlap with any other session of that user, running timer included. Completions follow the same rule: a game is completed only in the current season, and once its season is closed the completion is frozen too (**Cambiar fecha** and **Desmarcar** disappear and `PATCH /users/{username}/library/{id}/completion` answers 409). **Ratings:** a player can rate any game of their library from 1 to 100 (whole numbers), once per game whatever the seasons or platforms they played it on (table `game_scores`; sessions have no rating). It is offered right after completing a game in the profile, in a question (**¿Quieres puntuarlo?**, with **Ahora no**) that opens when a completion is confirmed in the home history and, at any time, with **Puntuar** / **Cambiar nota** on every row of the games list of the profile, where all the entries of the game show the same rating. A rated game shows its rating next to its name wherever the player's own games appear (the home history and timer card, the completion window, the most played games and the games list of the profile) as a small ring whose colour goes from red to green with the score. The admin panel (**Gestión de datos → Puntuaciones**) can create, change and delete any rating; deleting a user or a game removes theirs after the usual confirmation. Ratings of the others weigh a little in the recommendations (see below). A player cannot change the game of an existing session: they delete it and add it again. An admin can: **Gestión de datos → Sesiones → Editar → Juego** (a session logged on the wrong game); the session moves to the right game, which gets its library entry for that platform and season if it lacked one, and the old entry is removed when nothing is left in it (no session; one with a completion stays). The same follow-up applies when an admin changes a session's platform or start date. Manual changes check the user's achievements silently (nothing is announced to the group), and creating one also creates the library entry for that game/platform/season if it is missing.

## Abandoned games

A game of the running season that you are not going to finish can be marked as **abandoned**: in **Perfil → Resumen → Juegos**, its row has an **Abandonar** button, which asks "¿Seguro? Pulsa otra vez" like **Marcar completado** (and **Retomar** to take it back, with the same confirmation); on a phone, like the other buttons of the row, it shows only its icon. The row then shows an **Abandonado** tag instead of "En curso". It is reversible and silent (nothing is announced), and **playing the game again resumes it by itself** (a session starting after the mark), so there is nothing to undo. A completed game cannot be abandoned, completing an abandoned one just completes it, and, like completions, only the running season can be changed (a closed season keeps what it had). It is a note for the player: totals, rankings, streaks, achievements and recommendations do not change. An admin sees and can edit the raw mark in **Gestión de datos → Biblioteca** (**Abandonado el**).

## Exporting and importing your data

**Perfil → Ajustes → Tus datos** has **Descargar mis datos**, a `.json` file (`laviciacion-<usuario>-<fecha>.json`, `GET /users/{username}/export`) with what is yours: finished sessions, library entries (with their completions and abandoned marks), ratings, wishlist and the achievements you hold, plus the games and platforms those rows mention so the file means something on its own. It has no email, no Telegram id and nothing derived (totals, rankings, streaks, the time of an entry); a running timer is not in it.

**Importar datos…** is **switched off in the profile for now** (`IMPORT_ENABLED` in `front/js/pages/profile/data.js` hides it, and `IMPORT_ENABLED` in `api/src/routers/users.py` makes `POST /users/{username}/import` answer 404; the code stays). It takes such a file back (`POST /users/{username}/import`, yours or an admin's) and first shows what it would do (`?dry_run=true`: how many sessions, games, ratings and wishes are new, how many you already have, which cannot be imported and why) before asking for a yes. It is a **merge that never overwrites**: whatever the account already has wins, so importing the same file twice changes nothing; it follows the app's rules instead of bending them:

- sessions need the end after the start, not in the future, and no overlap with anything else you played (the first one wins); the duration is recomputed from the times; a session already there (same game and start) is counted, not added; each session opens the library entry it needs
- a player imports **the running season only**: rows of a closed season are reported and skipped (an admin imports any season, as with manual sessions)
- games and platforms are shared catalogues: a row whose game (looked up by id, then by name) or platform does not exist here is skipped and named in the report. An **admin's import** creates the missing games and platforms instead, which is how a file from another installation is brought in
- a completion keeps its date but stays one per game and season; ratings only for games you have (after the import) and the wishlist only for games you do not
- **achievements are not imported**: they are earned. After an import with new sessions the check runs silently in the background and awards the ones the sessions deserve
- the file is bounded (50,000 sessions, 8 MB through the proxy) and validated; one malformed row refuses the whole file before anything is written

The same panel section also offers the admin's full database copy, see [deployment.md](deployment.md#backups-and-restore).

## Audit log

**Sistema → Registro** in the admin panel lists what the admins have changed from the panel, newest first: when, who, a sentence ("Editó sesión #12", "Borró juego #hades", "Cambió los ajustes") and a **Ver** that unfolds how the row was before and what was sent. It can be filtered by admin, by section and by kind of action (create, edit, settings, delete). Only changes that went through are listed, secrets (passwords, tokens, API keys) never appear in it, and it does not record what players do on their own account. The log is read-only and is never edited or deleted from the panel. Technical details in [architecture.md](architecture.md#audit-log).

## Side menu

The button at the left of the top bar opens the menu, a panel that slides in from the left (on a phone and on a wide screen alike; the admin panel keeps its own sidebar). It lists **Principal** (Inicio, Actividad), **Explorar** (Juegos, Deseados, Logros, Jugadores and Estadísticas, marked WIP: a placeholder until the statistics are ready), **Tú** (Mi perfil, Ajustes: tabs of the profile; the recommendations are its third tab), **Administración** (admins only) and, at the foot, **Cerrar sesión**. It highlights the page you are on, closes with Escape, a tap outside, the close button or choosing a page, and its structure is in `front/js/lib/menu.js`. The top bar keeps only Inicio, the profile and, for admins, the admin panel.

## Players pages

**Jugadores** (menu → Explorar, `#/players`) lists the active players of the group: photo, name, total hours, games, completed, achievements and either what they are playing now (green aura) or when they played last; the ones playing come first, then the latest to play. Pressing one opens **their page**, `#/player/<id>`, with what is public: the figures of a season or of all of them (the same pills as the profile), most played games with their ratings, latest achievements and what they play now. It never shows the email, the Telegram id, the settings or the library detail, and a player who hides "playing now" (Ajustes) still appears, only without the live status. `GET /group/players` and `GET /group/players/{id}?season=`, derived; nothing is stored. Never the emergency account or inactive players.

## Achievements page

**Logros** (menu → Explorar, `#/achievements`) lists every achievement, but only the ones you have unlocked are shown: with its picture, a description (the text it announces with the player and the game made generic) and who of the group has unlocked it, how many times (once per season) and when last. The rest appear as "Logro oculto" (not even the name; the API sends only the id and `hidden: true`), with a count at the top. The same rule applies wherever achievements of other players show up: the public player page and the activity feed say "logro oculto" for what you have not unlocked. The admin panel always shows everything. `GET /group/achievements`, derived from the catalog and the unlocked achievements of the active players; nothing is stored.

## Games page

**Juegos** (menu → Explorar, `#/games`) lists every game of the database as cards (cover, name, genres, "En tu biblioteca", "Jugándose", how many players have it, the group's hours and the average rating), each one leading to the game's page. `GET /games/catalog` does the work on the server, derived and nothing stored: search by name; order by latest activity (default, the games nobody has touched last), most played, best rated, most players, release date or name; filters by genre and by your library (all, the ones you have, the ones you do not), and toggles for what is being played right now, games with players, completed by you and rated by you; 24 at a time with **Mostrar más**. **Añadir juego** opens the RAWG search of the timer picker and, once chosen, goes to the new game's page.

## Wishlist and upcoming releases

**Deseados** (menu → Explorar, `#/wishlist`) is the list of games you want to play, among them the ones that are not out yet, so there is one place for both and no extra screen. It has two halves: **Próximos lanzamientos** (games without a release date, or with a future one: the nearest first, with a countdown and the date; the ones without a date, shown as "Sin fecha confirmada", last) and **Quiero jugar** (already released, the latest wish first). Each card says which other players want the same game ("Lo quieren Bea y Cai") and has a × to take it off. `GET /group/wishlist`.

- **Adding**: **Añadir juego** uses the same RAWG search as the Juegos page (a game that is not in the database yet is created from RAWG after a confirmation), and the game's page has **Añadir a mi lista / Quitar de mi lista** when the game is not in your library. `PUT`/`DELETE /users/{username}/wishlist/{game_id}`, yours or an admin's; asking again is harmless, a game that is not in the database is a 404 and one that is already in your library a 409. Only games RAWG knows can be added (an announced game usually is, with a future date or none); a game RAWG does not have is not supported for now. The Juegos page marks the ones in your list ("En tu lista").
- **Only the wish is stored** (`users_wishlist`: user, game, when). Whether a game is upcoming, who else wants it and whether the wish is still pending are derived: **a game leaves the list by itself when it enters your library** (first session or manual session), the row is just ignored from then on. Only active players count, never the emergency account.
- **Release dates slip**: every day at 09:00 the scheduler (`daily_wishlist`) asks RAWG again for the date of each game somebody still waits for that is not out (or comes out today; one call per game, at most 50 per run) and writes a date only when RAWG gives one, never blanking it. Then it tells each player, by Telegram and push like the other private notices, which of the games they wished come out **today** and who else is waiting for them. Nothing is remembered between runs: a game comes out on one day only, and a day the API was down is not made up for (the 3 hours of grace of the daily jobs apply).

## Playing now

The navbar shows who else is playing right now: a chip with up to three avatars with a green aura (and "+N" for more), only when somebody is. Pressing it opens a bottom sheet on a phone (a normal window on a wide screen) with each player, the game, the platform and how long ago they started. Your own avatar gets the aura while your timer runs. When two or more players have a running timer on the same game (whatever the platform), the sheet shows them in one card, "Bea, Cai y tú estáis jugando a Hades" (you appear only when you are one of them); it only says they play the same game, not that they play together. Nothing is stored: it is the list of running timers of the active players (`GET /timers/now-playing`, never the emergency account), refreshed every 45 seconds while the app is visible, when it returns to the foreground and on every screen change. A timer running for more than **6 hours** is shown dimmed, after the others and with "¿Un timer olvidado?", and does not make the chip appear. Every player can stop appearing to the others in **Perfil → Ajustes → Jugando ahora** (on by default, `user_settings.show_playing`); they still see themselves. The photos come from `GET /users/photo/{id}`, readable by any logged-in user on purpose (only active players, only the image).

The installed app offers shortcuts on a long press of its icon (`shortcuts` in `front/manifest.json`): **Nuevo timer** (`#/new`, opens the game picker unless a timer is already running), **Jugando ahora** (`#/playing`, opens the sheet) and **Mi perfil**.

## Activity page

The **Actividad** page (menu → Principal, `#/activity`) lists what everybody has done, newest first and by day (Hoy, Ayer, then the date), 30 at a time with **Mostrar más** (`GET /activity?limit=&offset=`): hours played that day on a game, a game started for the first time, a game completed (with its rating, if any), a rating given and an achievement unlocked (with its game, if it has one). Within a day the most notable come first (completed, achievement, rated, started, played). Each line shows the player's photo and links to the game page. Only active players (never the emergency account); running timers are not events until they stop. Derived from the sessions, library, ratings and achievements; nothing is stored, so changing a rating moves it to its new date.

## Game page

Pressing a game's name (the history's unfolded rows, the profile's games list, most played and recommendations, the playing-now sheet) opens its page, `#/game/<id>` (`GET /games/{id}/overview`, any logged-in user): cover, genres, developer, release date and the average time to complete; the group's figures (players, hours, how many completed it, average rating and how many ratings); your own rating, which you can set or change there; and every active player who has it in their library (any season) with their hours, sessions, seasons, completions and rating, the most played first. A player gets the green aura and "Jugando ahora" while their timer runs (unless it is stale or they hide it, as in the chip). Derived from the library, sessions and ratings; nothing is stored.

## Profile figures and recommendations

The header of the profile shows the figures of the running season, with a pill per season the user has played and a **Total** pill (`GET /users/{username}/profile?season=2025|all`): stats, most played games, achievements and the list of games below them (`GET /users/{username}/library?season=2025`, every season for **Total**) follow the pill; the profile has three tabs, **Resumen**, **Recomendados** and **Ajustes**; the running streak is only shown for the running season and the total. Nothing is stored, each season is computed when asked.

The **Recomendados** tab of the profile shows 12 games (the bot, 10) picked at random among all the games other players have and you have never had (in any season). The chance of each one grows with how many players have it, how many completed it, the hours and the sessions the others have put into it, with how much you play its genres, and a little with the ratings (1-100) the others gave it: a well rated game is somewhat more likely and a badly rated one somewhat less, but only as far as enough players rated it, so a game with a single rating, or none, is hardly affected; every visit, or **Otras recomendaciones**, can show different ones, and the ones shown are listed with the most shared first. Nothing is stored: the candidates are computed from the libraries each time. When somebody completes a game, the group notice also suggests a game with a similar genre that somebody else has (written by the AI if OpenAI is configured, as a plain line if not).

## AI-written notices

The AI rewrites some notices of the group (a new game, a completed game, the rankings) in a funnier way; without it they go out as plain text. It is managed from the admin panel (**Sistema**, cards **Inteligencia artificial** and **Avisos que usan la IA**): an on/off switch, the provider (**Google Gemini** or **OpenAI**), the API key and, optionally, the model (empty: `gemini-2.5-flash` for Google, `gpt-4o-mini` for OpenAI). Changes apply at once, without restarting, and **Probar la IA** asks the saved configuration for one sentence and shows the answer or the reason it failed. The key is stored encrypted and never shown again.

`AI_PROVIDER`, `AI_API_KEY` and `AI_MODEL` in `.env` only **seed** these settings the first time the API starts. An installation that still has `OPENAI_API_KEY` / `OPENAI_MODEL` and no `AI_API_KEY` is seeded as an OpenAI setup, so it keeps working. Each notice that can use the AI has its own switch and its own editable instructions (prompt) under **Avisos que usan la IA**: a new game, a completed game (and the suggestion of another game it may carry), a change in the games ranking and a change in the hours ranking. The prompts in `api/src/utils/ai_prompts.py` are only the defaults: nothing is copied to the database until an admin edits one, from then on the edited text wins, and **Restaurar las originales** goes back to following the code (so an improved default reaches everybody who never changed it).
