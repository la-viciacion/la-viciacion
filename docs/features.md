# Features and how they behave

What the app does and the rules behind it, from the point of view of whoever runs it or uses it. The settings that go in `.env` are in [configuration.md](configuration.md); the code behind each rule is in [architecture.md](architecture.md).

## Seasons

A season is a calendar year. It is **never written by the app**: the `season` column of `users_games`, `game_timers` and `users_achievements` is generated by the database from the row's own date (`started_date`, `start_time`, `date`), so it can never disagree with it. To put a library entry or a session in another season, change its date. The running season is the year of today's date on the server (`api/src/utils/seasons.py`); keep `TZ` set so the season changes at local midnight.

The library of the 2023 and 2024 seasons (kept in the `_archived_users_games_*` tables since the yearly tables were retired) is restored into `users_games` by migration 011, so every past session has its library entry. The archive tables are left as they were.

## Notifications and scheduled jobs

Everything Telegram-related is managed from the admin panel (**Notificaciones → Ajustes**), not from `.env`:

- **Settings** live in the `app_settings` table: general notifications switch, admin-alerts switch (independent), weekly summary on/off + weekday + time, and the Telegram bot token, group id and admin chat id. The token is stored encrypted (key derived from `SECRET_KEY`; if you rotate `SECRET_KEY`, enter the token again) and the panel never shows it back. The token, the group id and the admin chat id are **locked**: the panel only says whether each one is set (`GET /manage/settings` returns `{is_set}`, never the value) and `PUT /manage/settings` refuses to change them; only the bot (logged in as the superadmin) reads it, through `GET /manage/settings/telegram`. `TELEGRAM_TOKEN`, `TELEGRAM_GROUP_ID` and `TELEGRAM_ADMIN_CHAT_ID` in `.env` only **seed** the table the first time the API starts.
- The **bot** reads its token and chats from the API and restarts itself (Docker brings it back) within about a minute when they change.
- **Scheduled jobs** run inside the API process (`api/src/utils/scheduler.py`), so no external cron is needed: weekly summary (private message to each active user with a Telegram id or a push device), (the pinned timer notification is only sent when the timer starts: its periodic refresh is switched off, `TIMER_NOTICE_REFRESH` in the scheduler), hourly forgotten-timer check that reminds once per timer (after 4 hours by default; each user can switch it off, choose whether it reaches them by Telegram and/or push, and choose their own whole number of hours, 1-24, in Profile → Ajustes → Notificaciones; a channel the user cannot be reached by, such as Telegram without a linked account or push without a device, does not count, and with none left no check is made), daily 05:00 check (announces the streaks lost the day before), daily 09:00 wishlist check (see [Wishlist](#wishlist-and-upcoming-releases)). Each run is recorded in `job_runs`, so a restart never repeats a run, and a job that was due while the API was down still runs when it returns (weekly summary: within 6 hours). Achievements and ranking announcements are event-driven: when a timer stops, a session or library entry changes (an admin's changes check the player silently) or an admin asks for it, everything is checked; when a timer starts, only what a running timer can unlock (early riser, nocturnal, new year, the release day of a game, the ones about the world outside the app, teamwork, all together) and the "new game" notice, once per game and season; completing a game also checks the completed-games achievements. Manual sessions never notify. Totals, rankings and streaks are never stored: they are computed from the sessions when requested, so a new season simply starts at zero.
- Each user can set their own Telegram id in their profile and admins can edit it for anyone; it is unique. The profile has a button that sends a private test message to the saved id (`POST /users/{username}/telegram-test`, only for oneself, ignores the notification switches) so the player can check it is right.

## Push notifications (installed PWA)

A second channel next to Telegram, **on by default**, with nothing to set up: the API creates its VAPID keys (one pair for the whole server, shared by all users) on the first start and uses `SMTP_EMAIL` as the contact towards the push services unless **Notificaciones → Avisos en la app (push)** sets another one or turns the feature off. It needs HTTPS. Nobody is subscribed automatically (browsers require a click and a permission per device): the app offers it once after login, and each user chooses for themselves, from their profile (**Ajustes → Notificaciones**, the devices card under the table of notices), which of their devices get notifications and whether each also gets the group ones; on iPhone/iPad the app must be added to the home screen first (iOS 16.4+).

- What goes to the Telegram group is also pushed to every device that has group notices on (a per-device switch); private notices (a forgotten timer, the weekly summary) go only to that user's devices.
- **Notificaciones → Redactar aviso** in the admin panel is a composer: title (80 characters) and message (240), with a live preview. Each notice goes through **one channel at a time**, chosen in the composer: the **app** (push: where a tap opens, an optional https image, to your own devices to try it, to one user, to the devices that want group notices or to every subscribed device) or **Telegram** (`POST /manage/telegram/announce`: to your own private chat, to one user's, or to the group; the title in bold, no link or image). Sending to a group or to everybody asks for confirmation. Plain text only; the image shows on Android and desktop, not on iPhone/iPad. These manual notices ignore the general notifications switch, like the test message. The **Avisos en la app** card of **Notificaciones → Ajustes** shows how many devices and users are subscribed.
- **Timer notification**: while you have a timer running, every subscribed device of yours shows a pinned, silent notification with the game and the time played, shown when the timer starts (its periodic refresh is switched off for now, and so is the interval setting in the profile). Tapping it, or its **Parar** button, opens the app, where you stop the timer (no button on iPhone/iPad). When the timer stops, from wherever, the notification turns into "Timer parado · 1h 25min". On iPhone/iPad it is refreshed but not pinned. It follows the general notifications switch and, for now, there is no per-device switch for it.
- Expired devices are removed automatically. Regenerating the keys unsubscribes every device.
- The pushed text is the same message as Telegram's without Markdown, cut to a title and a short body; how long messages and images fit is pending (see [roadmap.md](roadmap.md)).

## Platform catalogue

**Gestión de datos → Plataformas** in the admin panel manages the platform catalogue used by sessions and library entries: add one (its id is made from the name and never changes), rename it (everything that uses it follows), and delete one that nothing uses (a platform that still has sessions or library entries is refused and the message says how many). **Sesiones** and **Biblioteca** next to a platform jump to those rows.

## Revoking achievements

The pictures of the achievements come from the files of `api/achievement_images/`, which the API loads at every start (see [architecture.md](architecture.md)); a picture uploaded by hand from **Gestión de datos → Logros → Imagen…** is replaced at the next start if that achievement has a file there, so to change one for good, replace its file.

In the admin panel, **Gestión de datos → Logros**: pressing an achievement lists who has unlocked it and when. **Editar** changes the date it was obtained (its year is the season) and **Revocar** removes it without announcing anything. Achievements are re-evaluated on every check (after each stopped timer and after a change to the sessions or the library), so if the player still meets the condition it will be unlocked again: correct the data that triggered it first (e.g. a wrong session).

**Recalcular logros…** (the toolbar of **Logros**) works out again every achievement of every season from the sessions and the library, with the same rules as the live checks (`Achievements` in `collected` mode, `crud/achievements_recalc.py`), and brings what is stored to that: it **adds** what is missing, **corrects** the date or the game of what differs (a date edited by hand is calculated again) and **revokes** what no longer holds or is repeated. Everybody counts, active or not, never the emergency account, and the players, the seasons and the achievements to work out can be chosen (all by default, the switched-off ones always left alone: `user_ids`, `season_list` and `achievement_keys` in the API). **It never notifies anybody**, by construction: it does not go through the announcements at all. It takes two steps: a preview that lists exactly what it would add, correct and revoke (`GET /manage/recalculate-achievements/preview`, which changes nothing) and, after typing `RECALCULAR`, the recalculation itself in the background (`POST /manage/recalculate-achievements`; it works everything out again when it runs). Three achievements cannot be told apart from the sessions alone and are worked out in an approximate way: **Lo he abierto sin querer** from the earliest session of 5 minutes or less (a manual one cannot be told from a real timer), **Trabajo en equipo** from sessions of 4 or more different players that overlap (a forgotten timer counts as playing) and **Justo a tiempo** from the average time stored for each game (HLTB is not asked again).

**Editing or deleting a session of your own**, and **anything an admin creates, edits or deletes in a player's sessions or library** (**Gestión de datos → Sesiones** and **Biblioteca**), does the same recalculation, silently, for that player and the seasons involved (before and after the change, if it moved to another season): what it earned and no longer holds is revoked, and dates that moved are corrected, including dates edited by hand. Creating a manual session of your own only adds what it earns. The other players' achievements are not touched (a teamwork that depended on a deleted session stays for them until the next **Recalcular logros**).

## Manual sessions

From the home page a user can add a finished session by hand (**+ Sesión manual**: game, platform, start, end; before it is saved the form says how much time it adds, "Vas a añadir 1 h 30 min a «Doom»", and asks to confirm; changing a field asks again) and correct or delete one of their own from **Perfil → Resumen → Juegos → Sesiones** (the sessions of that game and season; **Editar**, only for the current season). In the home list of latest games, pressing a game's row unfolds its latest sessions (**Editar**, **Ver todas**), the complete mark (an empty circle in soft white, with no box, while the game is not completed this season; a filled green circle once it is) opens a window to mark it as completed (once per game and season, announced to the group; the window is the confirmation, so its **Marcar completado** completes with one press) and the play button starts a new timer. The API (`POST /timers/manual`, `PATCH`/`DELETE /timers/{id}`) enforces: the end after the start and not in the future, at most 24 h, **current season only** (closed seasons are frozen; admins can still edit them), and no overlap with any other session of that user. **A manual session is refused (409) while the user has a running timer**, whatever the times: they stop or cancel the timer first (the **+ Sesión manual** button is disabled while a timer runs). Completions follow the same rule: a game is completed only in the current season, and once its season is closed the completion is frozen too (**Cambiar fecha** and **Desmarcar** disappear and `PATCH /users/{username}/library/{id}/completion` answers 409). **Ratings:** a player can rate any game of their library from 1 to 100 (whole numbers), once per game whatever the seasons or platforms they played it on (table `game_scores`; sessions have no rating). It is offered right after completing a game in the profile, in a question (**¿Quieres puntuarlo?**, with **Ahora no**) that opens when a completion is confirmed in the home history and, at any time, with **Puntuar** / **Cambiar nota** on every row of the games list of the profile, where all the entries of the game show the same rating. A rated game shows its rating next to its name wherever the player's own games appear (the home history and timer card, the completion window, the most played games and the games list of the profile) as a small ring whose colour goes from red to green with the score. The admin panel (**Gestión de datos → Puntuaciones**) can create, change and delete any rating; deleting a user or a game removes theirs after the usual confirmation. Ratings of the others weigh a little in the recommendations (see below). A player cannot change the game of an existing session: they delete it and add it again. An admin can: **Gestión de datos → Sesiones → Editar → Juego** (a session logged on the wrong game); the session moves to the right game, which gets its library entry for that platform and season if it lacked one, and the old entry is removed when nothing is left in it (no session; one with a completion stays). The same follow-up applies when an admin changes a session's platform or start date. Manual changes check the user's achievements silently (nothing is announced to the group), and creating one also creates the library entry for that game/platform/season if it is missing.

## Abandoned games

A game of the running season that you are not going to finish can be marked as **abandoned**: in **Perfil → Resumen → Juegos**, its row has an **Abandonar** button, which asks "¿Seguro? Pulsa otra vez" like **Marcar completado** (and **Retomar** to take it back, with the same confirmation); on a phone, like the other buttons of the row, it shows only its icon. The row then shows an **Abandonado** tag instead of "En curso". It is reversible and silent (nothing is announced), and **playing the game again resumes it by itself** (a session starting after the mark), so there is nothing to undo. A completed game cannot be abandoned, completing an abandoned one just completes it, and, like completions, only the running season can be changed (a closed season keeps what it had). It is a note for the player: totals, rankings, streaks, achievements and recommendations do not change. An admin sees and can edit the raw mark in **Gestión de datos → Biblioteca** (**Abandonado el**).

## Exporting and importing your data

**Perfil → Ajustes → Tus datos** has **Descargar mis datos**, a `.json` file (`laviciacion-<usuario>-<fecha>.json`, `GET /users/{username}/export`) with what is yours: finished sessions, library entries (with their completions and abandoned marks), ratings, wishlist and the achievements you hold, plus the games and platforms those rows mention so the file means something on its own. It has no email, no Telegram id and nothing derived (totals, rankings, streaks, the time of an entry); a running timer is not in it.

**Importar datos…** is **switched off in the profile for now** (`IMPORT_ENABLED` in `front/js/pages/profile/data.js` hides it, and `IMPORT_ENABLED` in `api/src/routers/users.py` makes `POST /users/{username}/import` answer 404; the code stays). It takes such a file back (`POST /users/{username}/import`, yours or an admin's) and first shows what it would do (`?dry_run=true`: how many sessions, games, ratings and wishes are new, how many you already have, which cannot be imported and why) before asking for a yes. It is a **merge that never overwrites**: whatever the account already has wins, so importing the same file twice changes nothing; it follows the app's rules instead of bending them:

- sessions need the end after the start, not in the future, and no overlap with anything else you played (the first one wins); the duration is recomputed from the times; a session already there (same game and start) is counted, not added; each session opens the library entry it needs
- a player imports **the running season only**: rows of a closed season are reported and skipped (an admin imports any season, as with manual sessions)
- games and platforms are shared catalogues: a row whose game (looked up by id, then by name) or platform does not exist here is skipped and named in the report. An **admin's import** creates the missing games and platforms instead, which is how a file from another installation is brought in
- a completion keeps its date but stays one per game and season; ratings only for games you have (after the import) and the wishlist only for games you do not
- **achievements are not imported**: they are earned. After an import with new sessions the check runs silently in the background and awards the ones the sessions deserve
- the file is bounded (50,000 sessions, 8 MB through the proxy) and validated; one malformed row refuses the whole file before anything is written

The same panel section also offers the admin's full database copy, see [deployment.md](deployment.md#backups-and-restore).

## Audit log

**Sistema → Registro** in the admin panel lists what the admins have changed from the panel, newest first: when, who, a sentence ("Editó sesión #12", "Borró juego #hades", "Cambió los ajustes") and a **Ver** that unfolds how the row was before and what was sent. It can be filtered by admin, by section and by kind of action (create, edit, settings, delete). Only changes that went through are listed, secrets (passwords, tokens, API keys) never appear in it, and it does not record what players do on their own account. The log is read-only and is never edited or deleted from the panel. Technical details in [architecture.md](architecture.md#audit-log).

## Side menu

The button at the left of the top bar opens the menu, a panel that slides in from the left (on a phone and on a wide screen alike; the admin panel keeps its own sidebar). It lists **Principal** (Inicio, Actividad), **Explorar** (Juegos, Deseados, Recomendados, Logros, Jugadores and Estadísticas, marked WIP: a placeholder until the statistics are ready), **Tú** (Mi perfil, Ajustes: tabs of the profile), **Administración** (admins only) and, at the foot, **Cerrar sesión**. It highlights the page you are on, closes with Escape, a tap outside, the close button or choosing a page, and its structure is in `front/js/lib/menu.js`. The top bar keeps only Inicio, the profile and, for admins, the admin panel.

## Players pages

**Jugadores** (menu → Explorar, `#/players`) lists every player of the group: photo, name, total hours, games, completed and either what they are playing now (green aura) or when they played last; the ones playing come first, then the latest to play. Pressing one opens **their page**, `#/player/<id>`, with what is public: the figures of a season or of all of them (the same pills as the profile), most played games with their ratings, latest achievements and what they play now. It never shows the email, the Telegram id, the settings or the library detail, and a player who hides "playing now" (Ajustes) still appears, only without the live status. `GET /group/players` and `GET /group/players/{id}?season=`, derived; nothing is stored. Inactive players (who cannot log in or act) are listed and counted like the rest, marked with an "Inactivo" badge and a dimmed card (also on the player page and in the list of players of a game), with a Todos / Activos filter on the page; never the emergency account. Still left out of notices (push, Telegram, wishlist) and of who is playing now.

## Achievements catalogue

Every achievement is earned **once per season** and dated the day it was reached. "General" means the check that runs after a stopped timer, a change to sessions or library entries and an import. A session counts for a played day, a streak or the games of a day only when it lasts 10 minutes or more; hours add up whatever the length of each session. The texts, in Spanish, are in `api/src/utils/achievements.py` and then in the database (editable in the panel).

| Achievement | Condition | Evaluated |
|---|---|---|
| 4, 8, 12 and 16 hours in a day | Sum of the sessions that began that day | general |
| 8 hours in one game in a day | 8 h or more to one game in sessions that began the same day | general |
| 100, 500 and 1000 hours in a game | Hours in a game in the season (the game that got there first is named) | general |
| 100, 200, 500 and 1000 hours | Hours in the season | general |
| Lo he abierto sin querer | A timer stopped within 5 minutes (more than 0 s). Manual sessions and edits never earn it | when a timer stops |
| 4 and 8 hours in a session | A single session of 4 h or more, and one of 8 h or more | general |
| 10, 42, 50 and 100 games played | Distinct games in the library of the season (counted from the first timer) | when a timer starts, general |
| 1, 5, 10, 25, 42 and 100 games completed | Games completed in the season | when a game is completed, general |
| Del tirón | A game completed whose sessions of the season all began the same day | when a game is completed, general |
| Indecisión (5 and 10 games in a day) | Distinct games with sessions of 10 min or more that began the same day | general |
| 7, 15, 30, 60, 100, 200, 300 and 365 days played | Days touched by a session of 10 min or more (the day it began and the day it ended) | general |
| Streaks of 7, 15, 30, 60, 100, 200, 300 and 365 days | Consecutive played days; each is dated the day a run got to that length | general |
| El hijo pródigo | Back after 30 days or more without playing, inside the season | general |
| Semana laboral | 40 hours in a week (Monday to Sunday, each session counting on the day it began) | general |
| Feliz año nuevo | A timer that starts on 1 January, or a session that touches it | when a timer starts, general |
| Salvado por la campana | A session that was running when the year changed (31 December into 1 January); dated 1 January | general |

| Lo estaba esperando | A session of a game that began on the day the game came out (wished or not) | when a timer starts, general |
| Justo a tiempo | The time played in the season, within 5 % of the HLTB average of the game | when a game is completed |

| Trabajo en equipo | 4 or more players with a timer running when someone starts theirs | when a timer starts |
| Todos a una | 3 or more players with a timer running on the same game when someone starts theirs | when a timer starts |

Teamwork and "Todos a una" only count timers (never manual sessions) while they happen, and a forgotten timer still counts as playing. **Recalcular logros** works them out from the overlapping sessions instead.

**The world outside the app.** Fifteen achievements that depend on when and what was played, not on how much. All of them are hidden (secret), have no season limit (earned once in a lifetime) and begin to count in 2027 (`since`; only what was played from that season on counts, and nothing is awarded or announced before it), like any other, so the admin panel can change that. They are about the moment a timer **starts**, and they are judged right then (the same moment as early riser or the release day), whatever it ends up lasting: the 10-minute rule of the days and streaks does not apply, and a session that starts on one day and ends on the next belongs to the day it started. The general check (after a stopped timer or a change to the sessions, and **Recalcular logros**) judges the finished sessions by their start in the same way, so a manual session counts too and what a recalculation finds agrees with what a timer earned. **Nothing is stored for them but the award**: the days, the sky and the weather are worked out when asked (the weather is the one thing that comes from outside, see below).

- **The calendar** (`utils/external_events.py`): *Que la Fuerza te acompañe*, a timer started on the 4th of May with a Star Wars game (by its name, which has to say Star Wars or one of a few titles that do not, such as Jedi, Sith, Skywalker, Mandalorian, Old Republic, TIE Fighter, X-Wing or Battlefront, or by RAWG's tag "Star Wars"); *Mario Day*, the 10th of March with a game whose name has the word Mario (Super Mario, Mario Kart, Paper Mario, Dr. Mario...); *Un día que no existe*, the 29th of February (the first possible one is 2028); *Cumpleaños feliz*, the player's birthday (only if they entered their birth date; a 29th of February is celebrated on the 28th the years that have none). The two with a game name it in the notice.
- **The sky** (`utils/astronomy.py`, no API: Jean Meeus's formulas, accurate to a couple of minutes, the day is the server's local one): *Luna llena*, a day with a full moon; *Eclipse lunar* and *Eclipse solar*, the day of an eclipse **seen from the player's city** (they need to have chosen one; without it they cannot be earned): a solar one has to cover at least 0.25 of the Sun's diameter there with the Sun above the horizon (`astronomy.SOLAR_MIN_MAGNITUDE`; about 8 in 14 years from Madrid), a lunar one has to enter the umbra by at least 0.1 (global magnitude, so a barely noticeable bite does not count; `LUNAR_MIN_UMBRAL`) with the Moon above the horizon at its greatest (about 10 in 14 years from Madrid), and the timer has to start **in that night, after the sunset** at the player's city (from the sunset before the eclipse to the next sunrise, so one started at 1:00 after the eclipse's evening counts and one started at noon does not; the achievement is dated the day the timer started). The positions come from the `ephem` library, which carries its own tables (nothing is downloaded); and one achievement for each of the two equinoxes and the two solstices.
- **The age of a game**: *De la misma quinta*, a timer on a game that came out the year the player was born (it needs their birth date and the game's release date from RAWG); *Arqueólogo*, a timer on a game that was 25 years old or more the day it started (`external_events.ARCHAEOLOGIST_YEARS`; a game with no release date from RAWG never counts, so a wrong date there gives a wrong result).
- **The weather** (`utils/weather.py`, [Open-Meteo](https://open-meteo.com), free, no key): *Jugando bajo la tormenta*, a timer that starts in an hour with a thunderstorm (WMO codes 95, 96, 99) at the player's city, and *Niebla en Silent Hill*, one that starts in an hour with fog (45, 48) on a **horror** game. A game is a horror game when its RAWG tags say it (`games.tags`: RAWG has no Horror genre, only tags such as Horror or Survival Horror; the tags are filled in when a game is created and by the RAWG sync of the admin panel for the ones that have none). They need the player's **city**, which they choose in **Perfil → Ajustes → Mis datos**, as one more field of the form with their name, email and Telegram ID, with nothing that says what it is for: they type a name, pick one of the answers of Open-Meteo's geocoding (`GET /users/places/search`) and what is saved is its name and the coordinates of its centre, never a GPS fix; nobody else sees it, and without a city these two are not earned. Each past day is asked for once (the forecast service for the last 80 days, the archive for older ones, whose storm data is less reliable) and kept in `weather_days` (outside data, not derived from the sessions, so it may be stored); today is asked for again each time. If Open-Meteo does not answer, nothing is decided at that moment and the next check tries again (no request is made for five minutes after a failure); **Recalcular logros** leaves the weather ones exactly as they are for a player whose weather could not be had, instead of revoking them. The birthday needs the **fecha de nacimiento** of the same section (only the player and the admins see it; changing it and recalculating moves or revokes the award).

**No season limit.** Most achievements are earned once a season. The ones whose key ends in **`_LIFETIME`** are the exception: they count the whole history of a player (the hours of a game, the days, the games, the completions of every season added up) and are earned **once in a lifetime**. Which they are is written in their name, in `utils/achievements.py` (`is_lifetime`), with a test that fails if a key and its table of thresholds do not agree: there is no switch to change it. They are other achievements than the seasonal ones (the seasonal 500 and 1000 hours in a game stay as they are), so they are created like any new one, switched off in an installation that has some, and the panel marks them **Único** (the **Logros** page too, once unlocked). While none is switched on their checks cost nothing. **Recalcular logros** works them out once per player, whatever seasons are chosen, keeps the oldest if one was earned twice and files each in the season of its date.

**Valid from a season.** Each achievement says the season it starts to count in (**Desde** in the panel, `valid_from_season`). Before it nobody earns it and nothing is announced about it, **Recalcular logros** leaves what is stored in those seasons exactly as it is (it neither adds nor revokes), and the **Logros** page shows it only as a hidden one ("Logro oculto", with nothing about it, not even when it will begin, but with its aura if it is special), secret or not, unless the player already has it, so it is simply there, unlocked by nobody, when its season arrives (a switched-off one is not listed at all). The ones that existed before this was recorded are valid from **2023**, the first season of the app; every achievement has it in its definition (`since` in `utils/achievements.py`, 2023 for all of them: the ones added later are retroactive and count the history since the start; a test fails if one does not say it). It can be changed from the panel at any time. For the ones with no season limit (`_LIFETIME`) it also marks where the history they count begins: **only what was done from that season on counts** (the hours of a game, the days, the games), and they are not earned at all before it.

**Active or switched off.** Each achievement has an **Activo** switch (admin panel, **Logros**). A switched-off one is not earned by anybody, nothing is announced about it, **Recalcular logros** leaves it exactly as it is (it neither adds, corrects nor revokes it) and the **Logros** page does not show it, not even as a hidden one, unless the player already has it. What was earned before it was switched off is kept. An achievement the code no longer has (it was dropped) is switched off by itself at startup and never deleted. Everything is on by default: a new achievement starts active, and the season it is valid from (below) is what keeps it from counting before its time. Switching one on does not look back: use **Recalcular logros** to award the past, choosing that achievement. **Secret achievements.** An admin can mark an achievement as **Secreto** (admin panel, **Logros**; none is by default). A secret one is **hidden from whoever has not unlocked it**: the **Logros** page shows a locked "Logro oculto" (no title, text or picture; the API sends only the id, `hidden: true`, its level and **who has it**, names only, with no date and no count of times, so it is seen that it can be earned), and the public player page and the activity feed say "logro oculto" for it too. When somebody unlocks one, the group (Telegram and push) is only told "*Ana* ha desbloqueado un logro oculto" (with "Logro especial de nivel N" on top if it is special): no title, text, game or picture. The player gets the whole notice **privately**, on every channel they have (Telegram if they linked an account, push if they have a device), unless the notifications are off or the check is silent (a recalculation never notifies). With several players at once (teamwork, "Todos a una") the group gets one message naming them and each gets their own. Whoever has it sees it in full with a "Secreto" tag and can see who else has it, like the rest. **Special achievements.** Independently of being secret, an achievement can be **Especial** at one of three levels (`achievements.special`, 0 = ordinary), and each level is a colour: **1 plateado, 2 dorado, 3 morado**. A special one shines with an **aura of its colour** (and a tag that says so) on the **Logros** page and in the lists of achievements of a profile, **whether it is unlocked or not**, so that everybody knows there are special ones to aim for: a locked special one is a locked card with only its aura. Every special one is secret too, so when somebody unlocks one the group is told "ha desbloqueado un logro oculto" with the level on top ("Logro especial de nivel 2": it says how rare it is and nothing about what it is), and the player's private notice has the whole message with the same first line. An achievement is **secret** when it is marked as such or when it is special (`Achievement.is_secret`, derived: a special one is as hidden as a secret one, and raising the level of one hides it without touching its mark), so it is hidden, special or both, never special and visible.

**Which are special and which are secret.** The definition of each achievement in `utils/achievements.py` says it (`special`: 1 to 3, `secret`: true; neither when it says nothing), and an installation creates it like that; an admin can change either afterwards, and the database is the truth. A level reflects how hard or rare it is to earn: 1 silver is a clear effort or an uncommon coincidence, 2 gold is months of constancy or something very rare, 3 purple is nearly out of reach. The levels, by family: **in a day** 12 h (1) and 16 h (2); **in a game in a season** 100 h (1), 500 h (2) and 1000 h (3); **hours in a season** 500 (1) and 1000 (2); **games played** 42 and 50 (1) and 100 (2); **games completed** 25 (1), 42 (2) and 100 (3); **10 games in a day** (1); **days played** 200 (1), 300 (2) and 365 (3); **streaks** 100 and 200 (1), 300 (2) and 365 (3); **with no season limit** 1000 h in a game (2), days 1000 (1), 2000 (2) and 5000 (3), hours 2000 (1), 5000 (2) and 10000 (3), games played 500 (1) and 1000 (2), games completed 500 (2) and 1000 (3); **others** "Lo estaba esperando", "Semana laboral", "Salvado por la campana", "Justo a tiempo" and "Trabajo en equipo" (1); **the world outside the app** the storm, the 29th of February and "De la misma quinta" (1), the fog with a horror game (2) and the two eclipses (3). They are valid from 2027, and until then they are listed as hidden ones with that aura. Every special one is secret too. Marked as secret besides: "Media jornada, 12 horas", "Sesión de 4 horas", "La respuesta (de verdad)", "Indecisión x2", days played 200, 300 and 365, "Del tirón", "Trabajo en equipo", "Feliz año nuevo", "Salvado por la campana", "Madrugador", "Plus por nocturnidad", "Justo a tiempo" and every one about the world outside the app. Migration 029 gave the first set of values to the rows an installation already had and 033 the review of the whole catalogue, both only where nobody had changed them.

## Achievements page

**Logros** (menu → Explorar, `#/achievements`) lists every achievement, with its picture, a description (the text it announces with the player and the game made generic) and who of the group has unlocked it (including players who no longer play), how many times (once per season) and when last. The ones you have not unlocked are shown **dimmed with their name only, not the description nor the picture** (a placeholder trophy stands in; the API sends neither, nor the key, because the picture and the key would give away what it is about; they come once you have unlocked it in any season), so you have to work out what they are about, unless they are secret: those appear as "Logro oculto" (see below), with a count at the top. The same rule applies wherever achievements of other players show up: the public player page and the activity feed say "logro oculto" only for the secret ones you have not unlocked. The admin panel always shows everything. `GET /group/achievements`, derived from the catalog and the unlocked achievements of every player; nothing is stored. The page has **two blocks**: **De temporada** (earned once a season, counting only what was played in it) and **Lifetime** (key ending in `_LIFETIME`: they count the whole history and are earned once), each with its own "Tienes X de Y" and a header that folds it (open by default; it stays as left while you change season). The season block has **a pill per season** (from 2023 to the running one, the running one by default, like the profile's): each shows only the achievements that existed and were active that season, who of the group earned them **in that season** (so no "×2"), whether you did, and, for the running season only, your progress; `GET /group/achievements?season=<year>`, a future season is a 400. What you have earned in another season does not count as earned in this one, but it does tell you what the achievement is (its description and, if it is secret, its name show), because you have unlocked it once. The lifetime block does not depend on the pill; an empty block is not shown, and a hidden secret one goes in the block it belongs to (the API sends only that, `lifetime`). **Progress bars:** an achievement that adds something up and that you do not have yet shows a bar and "35 / 100" (no unit on purpose: a locked achievement does not say what it counts): total hours, days played, games played, games completed, hours in a single game (season ones count the running season, so one earned in a past season shows how far this season is; lifetime ones count the whole history from the season they start in) and the **current** streak. The ones about a moment (hours in a day, a session, early riser...) and the secret ones have no bar. `progress` of `GET /group/achievements` comes from the same queries and thresholds the checks use (`crud/achievement_progress.py`), so a bar and the unlock agree; nothing is stored.

## Games page

**Juegos** (menu → Explorar, `#/games`) lists every game of the database as cards (cover, name, genres, "En tu biblioteca", "Jugándose", how many players have it, the group's hours and the average rating), each one leading to the game's page. `GET /games/catalog` does the work on the server, derived and nothing stored: search by name; order by latest activity (default, the games nobody has touched last), most played, best rated, most players, release date or name; filters by genre and by your library (all, the ones you have, the ones you do not), and toggles for what is being played right now, games with players, completed by you and rated by you; 24 at a time with **Mostrar más**. **Añadir juego** opens the RAWG search of the timer picker and, once chosen, goes to the new game's page.

## Wishlist and upcoming releases

**Deseados** (menu → Explorar, `#/wishlist`) is the list of games you want to play, among them the ones that are not out yet, so there is one place for both and no extra screen. It has two halves: **Próximos lanzamientos** (games without a release date, or with a future one: the nearest first, with a countdown and the date; the ones without a date, shown as "Sin fecha confirmada", last) and **Quiero jugar** (already released, the latest wish first). Each card says which other players want the same game ("Lo quieren Bea y Cai") and has a × to take it off. `GET /group/wishlist`.

- **Adding**: **Añadir juego** uses the same RAWG search as the Juegos page (a game that is not in the database yet is created from RAWG after a confirmation), and the game's page has **Añadir a mi lista / Quitar de mi lista** when the game is not in your library. `PUT`/`DELETE /users/{username}/wishlist/{game_id}`, yours or an admin's; asking again is harmless, a game that is not in the database is a 404 and one that is already in your library a 409. Only games RAWG knows can be added (an announced game usually is, with a future date or none); a game RAWG does not have is not supported for now. The Juegos page marks the ones in your list ("En tu lista").
- **Only the wish is stored** (`users_wishlist`: user, game, when). Whether a game is upcoming, who else wants it and whether the wish is still pending are derived: **a game leaves the list by itself when it enters your library** (first session or manual session), the row is just ignored from then on. Only active players count, never the emergency account.
- **Release dates slip**: every day at 09:00 the scheduler (`daily_wishlist`) asks RAWG again for the date of each game somebody still waits for that is not out (or comes out today; one call per game, at most 50 per run) and writes a date only when RAWG gives one, never blanking it. Then, **only while `actions.WISHLIST_PRIVATE_NOTICE` is on (it is off for now: the group is told the day before, see below)**, it tells each player, by Telegram and push like the other private notices, which of the games they wished come out **today** and who else is waiting for them. Nothing is remembered between runs: a game comes out on one day only, and a day the API was down is not made up for (the 3 hours of grace of the daily jobs apply).
- **The day before, to the group**: every day at 12:30 (`wishlist_eve`, after the 09:00 refresh, so a date that slipped is already corrected) one message goes to the group, like the other group notices (Telegram and push), naming each wished game that comes out **tomorrow** and who waits for it. Nothing is sent if there is none. It can be rewritten by the AI (use `wishlist_release`, "Sale un juego deseado": switch and prompt in the admin panel like the others; without the AI it is the plain text). Same grace window and no catch-up as above.

## Playing now

The navbar shows who else is playing right now: a chip with up to three avatars with a green aura (and "+N" for more), only when somebody is. Pressing it opens a bottom sheet on a phone (a normal window on a wide screen) with each player, the game, the platform and how long ago they started. Your own avatar gets the aura while your timer runs. When two or more players have a running timer on the same game (whatever the platform), the sheet shows them in one card, "Bea, Cai y tú estáis jugando a Hades" (you appear only when you are one of them); it only says they play the same game, not that they play together. Nothing is stored: it is the list of running timers of the active players (`GET /timers/now-playing`, never the emergency account), refreshed every 45 seconds while the app is visible, when it returns to the foreground and on every screen change. A timer running for more than **6 hours** is shown dimmed, after the others and with "¿Un timer olvidado?", and does not make the chip appear. Every player can stop appearing to the others with `user_settings.show_playing` (on by default); the profile does not offer it for now (`SHOW_PLAYING_OPTION` in `front/js/pages/profile/index.js`, off), but the setting still works through the API. They still see themselves. The photos come from `GET /users/photo/{id}`, readable by any logged-in user on purpose (only active players, only the image).

The installed app offers shortcuts on a long press of its icon (`shortcuts` in `front/manifest.json`): **Nuevo timer** (`#/new`, opens the game picker unless a timer is already running), **Jugando ahora** (`#/playing`, opens the sheet) and **Mi perfil**.

## Activity page

The **Actividad** page (menu → Principal, `#/activity`) lists what everybody has done, newest first and by day (Hoy, Ayer, then the date), 30 at a time with **Mostrar más** (`GET /activity?limit=&offset=`): hours played that day on a game, a game started for the first time, a game completed (with its rating, if any), a rating given and an achievement unlocked (with its game, if it has one). Within a day the most notable come first (completed, achievement, rated, started, played). Each line shows the player's photo and links to the game page. Every player, active or not (never the emergency account); running timers are not events until they stop. Derived from the sessions, library, ratings and achievements; nothing is stored, so changing a rating moves it to its new date.

## Game page

Pressing a game's name (the history's unfolded rows, the profile's games list, most played and recommendations, the playing-now sheet) opens its page, `#/game/<id>` (`GET /games/{id}/overview`, any logged-in user): cover, genres, developer, release date and the average time to complete; the group's figures (players, hours, how many completed it, average rating and how many ratings); your own rating, which you can set or change there; and every active player who has it in their library (any season) with their hours, sessions, seasons, completions and rating, the most played first. A player gets the green aura and "Jugando ahora" while their timer runs (unless it is stale or they hide it, as in the chip). Derived from the library, sessions and ratings; nothing is stored.

## Profile figures and recommendations

The profile has the layout of the admin panel: a side menu (a collapsible bar on a phone) with two sections, **Resumen** (the default) and **Ajustes**, under a header with the photo and the name. Resumen shows the figures of the running season, with a pill per season the user has played and a **Total** pill (`GET /users/{username}/profile?season=2025|all`): stats, most played games, achievements and the list of games below them (`GET /users/{username}/library?season=2025`, every season for **Total**) follow the pill; the running streak is only shown for the running season and the total. Nothing is stored, each season is computed when asked.

The **Recomendados** page (menu → Explorar, `#/recommendations`) shows 12 games (the bot, 10) picked at random among all the games other players have and you have never had (in any season). The chance of each one grows with how many players have it, how many completed it, the hours and the sessions the others have put into it, with how much you play its genres, and a little with the ratings (1-100) the others gave it: a well rated game is somewhat more likely and a badly rated one somewhat less, but only as far as enough players rated it, so a game with a single rating, or none, is hardly affected; every visit, or **Otras recomendaciones**, can show different ones, and the ones shown are listed with the most shared first. Nothing is stored: the candidates are computed from the libraries each time. When somebody completes a game, the group notice also suggests a game with a similar genre that somebody else has (written by the AI if OpenAI is configured, as a plain line if not).

## AI-written notices

The AI rewrites some notices of the group (a new game, a completed game, the rankings) in a funnier way; without it they go out as plain text. It is managed from the admin panel (**Sistema**, cards **Inteligencia artificial** and **Avisos que usan la IA**): an on/off switch, the provider (**Google Gemini** or **OpenAI**), the API key and, optionally, the model (empty: `gemini-2.5-flash` for Google, `gpt-4o-mini` for OpenAI). Changes apply at once, without restarting, and **Probar la IA** asks the saved configuration for one sentence and shows the answer or the reason it failed. The key is stored encrypted and never shown again.

`AI_PROVIDER`, `AI_API_KEY` and `AI_MODEL` in `.env` only **seed** these settings the first time the API starts. An installation that still has `OPENAI_API_KEY` / `OPENAI_MODEL` and no `AI_API_KEY` is seeded as an OpenAI setup, so it keeps working. Each notice that can use the AI has its own switch and its own editable instructions (prompt) under **Avisos que usan la IA**: a new game, a completed game (and the suggestion of another game it may carry), a change in the games ranking and a change in the hours ranking. What the AI knows is only the message of the notice, and what it keeps is what its prompt asks: the notice of a completed game says who, the number of games completed this season, the game, **how long it took the player** and, when it is known, the average time to complete it, and its prompt asks the AI to keep the player's time and the average and to speak of the player in the third person (the notice goes to the group, not to them) (`tests/test_notice_contracts.py` pins, for every notice, what its message carries against what its prompt asks). The prompts in `api/src/utils/ai_prompts.py` are only the defaults: nothing is copied to the database until an admin edits one, from then on the edited text wins, and **Restaurar las originales** goes back to following the code (so an improved default reaches everybody who never changed it).
